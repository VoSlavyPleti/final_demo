    Термин

    Что означает

    Процесс

    оркестрируемая операция уровня сессии целиком — создание сессии или её завершение. У процесса есть чёткий финал: сессия становится READY, TERMINATED или FAILED

    Подпроцесс (sandBox = linux process)

    Песочница агента sandBox

    rootfs

    папка на сервере AEF WorkStation, которая внутри песочницы становится корнем файловой системы «/»: путь (/workspace — подпапка внутри неё)

    /workspace

    единственный каталог песочницы, который сохраняется; берутся только обычные файлы, симлинки и пустые папки пропускаются

    scopeId

    адрес ячейки хранения, по которому файлы находятся между сессиями; приходит от агента в теле запроса на создание сессии (подробнее — «Как формируется ключ объекта»)

    Ревизия (revision)

    неизменяемый слепок /workspace; идентификатор — случайные 32 символа, а не порядковый номер

    Снапшот (snapshot)

    подпроцесс создания ревизии: файлы, за ними манифест, затем указатель latest.json — который обновляется не всегда, см. «Вытеснение»

    Restore

    обратный подпроцесс: /workspace очищается и заполняется файлами ревизии; каждый файл сверяется по отпечатку и размеру, несовпадение прерывает создание сессии

    Манифест

    JSON-опись ревизии: какие файлы и где лежит содержимое каждого; пишется двумя объектами — ревизией и копией в latest.json

    latest.json (указатель)

    объект с копией манифеста текущей ревизии ячейки; restore читает только его, список объектов сервис не запрашивает

    Блоб (blob)

    содержимое одного файла, лежащее в S3 отдельным объектом

    objectKey

    поле манифеста с полным ключом блоба; restore идёт по нему, а не собирает ключ заново

    sha256

    отпечаток содержимого, 64 символа: одинаковые файлы дают одинаковый отпечаток, разные — разный

    Контент-адресуемое хранилище

    приём, при котором имя объекта равно отпечатку его содержимого

    Дедупликация

    одинаковые файлы дают один ключ и занимают одно место; раздел blobs/ общий для всех ячеек, поэтому это работает и между разными агентами

    sessionCreatedAt

    время создания сессии в манифесте; по нему выбирается текущая ревизия — побеждает сессия, созданная позже

    parentRevisionId

    из какой ревизии стартовала сессия; только для диагностики

    Вытеснение (supersede)

    снапшот записан, но указатель не обновлён из-за более свежей сессии; штатный исход, не ошибка

    schemaVersion

    версия формата манифеста, сейчас 2; манифесты версии 1 читаются, но вытесняются любым новым снапшотом

    TTL / idle timeout

    сроки автоматического завершения сессии: предельный срок жизни (1 час) и простой без обращений (15 минут)

    cleanup-worker

    фоновый воркер: завершает просроченные сессии и повторяет неудавшиеся снапшоты раз в 60 секунд

    ConfigMap / secman

    механизмы Kubernetes: откуда сервис берёт несекретные настройки и, отдельно, секреты

    S3 — это опция долговременной памяти агента

    S3 (Simple Storage Service) — это объектное хранилище .

    • S3 — дополнительная возможность AEF WorkStation, которая даёт агенту долговременную память артефактов сессии агента.

      • Она не является обязательной: AEF WorkStation (рабочая станция) полностью работоспособна без неё. По умолчанию она выключена ( WORKSPACE_STORE_ENABLED=false ) и включается командой разработки агента , когда агенту нужно сохранять файлы между сессиями в объектном хранилище S3.

    • Если опция выключена — данные хранятся только временно (TTL SandBox session настраивается в AEF WorkStation).

      • Всё, что агент записал в файлы, существует ровно столько, сколько живёт sandBox сессия (настраиваемый параметр): до явного завершения, до истечения предельного срока жизни или до отключения по простою. После этого каталог удаляется целиком и содержимое восстановить нельзя.

    Зачем S3 нужен для AEF WorkStation

    1. Сессия AEF WorkStation (sanBox session) — это песочница, под запрос агента создаётся отдельный каталог, который служит для него корневой файловой системой (в коде — rootfs), и при завершении сессии или по TTL этот каталог удаляется целиком, поэтому всё, что агент положил в файлы, по умолчанию исчезает вместе с ним;

    2. S3 — внешнее объектное хранилище: при завершении сессии AEF WorkStation выгружает туда содержимое /workspace, при создании новой сессии с тем же scopeId — возвращает обратно. Это единственная точка долговременного хранения пользовательских файлов в системе;

    3. Привязка идёт не к сессии, а к долгоживущему scopeId: сервис не разбирает его содержимое, а использует как адрес ячейки. Агент может завершить сессию, вернуться через час с тем же scopeId и увидеть свои файлы на месте;

    4. S3 превращает песочницу с кратковременной памятью в рабочий каталог, который сохраняется между сессиями — это единственная точка долговременного хранения пользовательских файлов в системе.

    Как формируется ключ объекта

    • В S3 нет папок. Каждый объект лежит в бакете под одним длинным именем — это имя и называется ключом, и обратиться к объекту можно только по нему целиком.

      • Ключ похож на путь к файлу (workstation/workspaces/blobs/3a/...), но сходство внешнее: слеши в нём — обычные символы имени, а не вложенные каталоги. Имя бакета частью ключа не является, оно указывается в запросе отдельно. Ключ целиком составляет рабочая станция.

    • Всего используется три ключа.

      • Ключ блоба. Формируется при снапшоте. Это адрес содержимого одного файла: именем объекта служит отпечаток его байтов.

      • Ключ ревизии. Формируется при снапшоте, каждый раз новый. Это адрес описи одного сохранённого слепка /workspace, и прежние описи новый ключ не затирает.

      • Ключ указателя. Записывается при снапшоте и читается при восстановлении. Это адрес описи того слепка, который считается для ячейки текущим.

    Гарантия безопасности получения артефактов агента из S3:

    • Имя объекта с содержимым не выбирается произвольно — оно вычисляется из самих байтов файла. Отпечаток sha256 устроен так, что изменение даже одного байта даёт другой отпечаток, а значит и другой ключ. Положить по существующему ключу другое содержимое, не разорвав эту связь, невозможно.

    • Проверяется связь при каждом восстановлении. Рабочая станция скачивает объект, заново считает отпечаток от полученных байтов и сверяет его с описью, а заодно сверяет размер. Совпало — файл раскладывается в /workspace; не совпало — восстановление прерывается и сессия не создаётся. Половинчатого результата не бывает: агент получает либо ровно то, что было сохранено, либо ничего.

    • Отдельно проверяется, куда файл кладётся. Итоговый путь дополнительно проверяется на то, что он не вышел за пределы /workspace. Подменённая опись не сможет заставить станцию записать файл в системный каталог песочницы.

    Пример ключа в составе

    Ключ содержимого файла (блоба) — шаблон и подстановка:

    Bucket = {bucket} <- отдельный параметр запроса, в ключ НЕ входит
    Key = {prefix}/blobs/{sha256[:2]}/{sha256}
    | | | |
    | | | +-- полный отпечаток содержимого, 64 символа
    | | +--------------- первые 2 символа отпечатка: раскладывают
    | | объекты по 256 подразделам
    | +--------------------- постоянный раздел, зашит в коде
    +------------------------------ из ConfigMap, может быть пустым
     
    Bucket = aef-workstation
    Key = workstation/workspaces/blobs/3a/3a7f9c4e8b1d...e21

    Ключ манифеста ревизии — шаблон и подстановка:

    Bucket = {bucket}
    Key = {prefix}/scopes/{scopeId}/revisions/{revisionId}.json
    | | | | |
    | | | | +-- 32 символа, новый при каждом снапшоте
    | | | +------------ постоянный раздел, зашит в коде
    | | +---------------------- ОТ АГЕНТА: адрес ячейки хранения
    | +----------------------------- постоянный раздел, зашит в коде
    +-------------------------------------- из ConfigMap, может быть пустым
     
    Bucket = aef-workstation
    Key = workstation/workspaces/scopes/3c8f9f4d8b6a/revisions/9f2c4e81a7b3.json

    Ключ указателя — шаблон и подстановка:

    Bucket = {bucket}
    Key = {prefix}/scopes/{scopeId}/latest.json
    | | | |
    | | | +-- постоянное имя: указатель у ячейки один
    | | +------------ ОТ АГЕНТА: адрес ячейки хранения
    | +------------------- постоянный раздел, зашит в коде
    +---------------------------- из ConfigMap, может быть пустым
     
    Bucket = aef-workstation
    Key = workstation/workspaces/scopes/3c8f9f4d8b6a/latest.json

    • Откуда приходит scopeId. агент передаёт его полем workspacePersistence.scopeId в теле запроса POST /v1/sessions. Станция принимает значение как есть и использует только как адрес — не путать с sessionId, тот приходит заголовком X-Session-Id и живёт одну сессию.

    • В каком виде. Это произвольная строка от 1 до 128 символов: не UUID и не число, формат ничем не задан. Проверяется только длина, состав символов — нет, поэтому слеш внутри создаст в бакете лишние уровни вложенности, а сырой пользовательский sessionKey передавать нельзя: значение попадает и в ключ объекта, и в логи.

    • Что это за уникальность. scopeId уникален не для сессии, а для набора файлов: он именует ячейку хранения, и весь его смысл в повторном использовании — тот же scopeId в новой сессии означает обращение к тем же файлам. Отвечает за уникальность вызывающая сторона (агент)

    Точка в коде

    • сразу после создания rootfs

    • Процесс создания сессии: rootfs создан → подпроцесс: S3 restore (GetObject) → сессия → READY

    • до удаления rootfs

    • Процесс завершения сессии: сессия → TERMINATING → подпроцесс: S3 snapshot (PutObject) → rootfs удалён → TERMINATED

    Операции S3

    • S3 АПИ GetObject — «дай один объект».

    • За один запрос приходит ровно ОДИН файл. (Получить несколько файлов одним запросом нельзя.)

    • S3 АПИ PutObject — «положи один объект».

    • За один запрос уходит ровно ОДИН файл. (Отправить несколько файлов одним запросом нельзя.)

    Из входящего запроса (заголовок X-Trace-Id или traceparent от гейтвея); если не пришло — станция генерирует сама.

    Сквозной идентификатор действия агента — по нему лог станции и сам вызов к S3 связываются с тем, что происходило на гейтвее

    Идентификатор конкретного HTTP-запроса (в отличие от X-Trace-Id, который общий на всё действие агента)

    string

    0..1

    Сначала берётся настройка AGENT_ID самой станции; если не задана — значение из входящего запроса.

    traceparent

    string, формат W3C Trace Context (00-<trace-id>-<span-id>-<flags>)

    0..1

    Копируется из входящего запроса как есть, без изменений. У фоновых задач не появляется — нет входящего запроса, откуда его взять

    Стандартный заголовок трассировки W3C — тот же trace-id, что и в X-Trace-Id, но в формате для систем, которые понимают именно его

    P.s В обоих случаях выгрузка идёт до удаления песочницы — иначе файлы исчезнут до загрузки в S3.

    При завершении sandBox сессии в S3 уходит:

    Что

    Сколько

    содержимое каждого файла — как есть, без изменений

    по одному объекту на файл

    опись (в коде — манифест): какой файл как назывался, где искать его содержимое, какие права и время изменения

    один объект на всю сессию, отправляется последним

    1. Сохранение в S3 - это подпроцесс внутри процесса завершения сессии, а не самостоятельный вызов API — он всегда выполняется как один из шагов _terminate_existing_session, до перехода сессии в TERMINATED

    2. Какие именно файлы — это любой обычный файл, физически лежащий в /workspace на момент завершения сессии (не важно, создал его агент сам или загрузил пользователь через API).

      1. Пустые папки и символические ссылки не сохраняются — только обычные файлы.

    3. Если сохранение оборвалось на середине — опись просто не появится. А без описи рабочая станция не видит эту попытку сохранения вовсе и при следующем запуске возьмёт предыдущую целую версию.

      1. Наполовину сохранённых данных агенту никогда не подсовывают.

    4. Папка сессии не удаляется, пока сохранение не пройдёт успешно — система пробует снова каждую минуту, без ограничения по числу попыток.

      1. Если сервер перезапустят раньше, чем получится сохранить — несохранённые файлы теряются, потому что папка сессии по умолчанию не переживает такой перезапуск.

    Копируется из входящего запроса как есть, без изменений. У фоновых задач не появляется — нет входящего запроса, откуда его взять

    Стандартный заголовок трассировки W3C — тот же trace-id, что и в X-Trace-Id, но в формате для систем, которые понимают именно его
