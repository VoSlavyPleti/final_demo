    1. Описание сервиса

    1.1 Назначение

    AEF WorkStation предназначен для предоставления AI-агенту безопасной, изолированной рабочей среды, в которой можно выполнять команды, запускать код и работать с файлами.

    Агент не управляет runtime-механизмами напрямую и не работает с файловой системой хоста. Взаимодействие клиента с AEF WorkStation выполняется только через REST API. # Контракт универсального агента для отправки в систему мониторинга

    1.2 Основные функции сервиса

    Шаг

    Действие

    Метод

    1

    Создать sandbox-сессию

    POST /v1/sessions

    2

    Получить состояние sandbox-сессии

    3

    2. Сессии

    2.1 Авторизация операций в рамках сессии

    Метод POST /v1/sessions является стартовым: bearer-token для него не существует, потому что сессия ещё не создана.

    Этот метод может быть закрыт общим секретом. Если IS_CREATE_SESSION_SECRET=true, запрос обязан содержать заголовок X-Session-Create-Secret со значением, совпадающим с SESSION_CREATE_SECRET; иначе создание отклоняется. По умолчанию проверка выключена, и метод доступен без каких-либо заголовков. Секрет общий для вызывающей стороны, а не для сессии: он отвечает на вопрос «наш ли это клиент», но не «имеет ли клиент право на эту ячейку хранения». Сервис не стартует, если проверка включена, а значение секрета пустое.

    Все остальные методы работы с sandbox-сессией требуют авторизацию по bearer-token.

    Проверки

    Сервис должен проверить:

    Проверка

    Условие успешности

    Наличие token

    Header Authorization передан и содержит bearer-token

    Наличие X-Session-Id

    Header X-Session-Id передан

    Совпадение идентификаторов

    X-Session-Id равен session_id в path

    Соответствие token

    Hash переданного token совпадает с hash, связанным с сессией

    Если хотя бы одна проверка не пройдена, операция не выполняется.

    Для POST /v1/sessions действует отдельная проверка: при включённом IS_CREATE_SESSION_SECRET сверяется заголовок X-Session-Create-Secret. Сравнение выполняется в постоянном времени, само значение секрета не попадает ни в ответ, ни в логи.

    Сессия создаётся

    ready

    Сессия готова к рабочим операциям

    terminating

    Сессия завершается

    terminated

    Сессия завершена

    failed

    Сессия не смогла быть создана или восстановлена

    Разрешённость операций:

    Операция

    Разрешённые статусы

    get session

    provisioning, ready, terminating, terminated, failed

    terminate

    exec

    ready

    exec:stream

    files:upload

    files:download

    files:list

    Если операция не разрешена в текущем статусе, сервис возвращает ошибку invalid-state.

    Авторизация не требуется для служебных путей: /health/liveness, /health/readiness, /version, /metrics, /docs, /redoc, /openapi.json.

    Переходы между статусами ограничены отдельно от разрешённости операций:

    Из статуса

    terminating

    terminated

    failed

    Переход из terminated и failed обратно в provisioning — это повторное использование того же идентификатора сессии: рабочая среда создаётся заново.

    3. Изоляция сессии

    Сервис должен применять ограничения безопасности до выполнения операции.

    Ограничение

    Что защищает

    Запрет path traversal

    Нельзя выйти за пределы rootfs сессии

    Нормализация виртуальных путей

    Все file/exec пути приводятся к безопасному виду

    Deny-list команд

    Запрещаются опасные команды и shell payload tokens: sudo, mount, iptables, docker, podman. Проверяется и сама команда, и то, что передано в sh -lc

    Allowlist исполняемых файлов

    Короткое имя команды резолвится только в пути из EXEC_ALLOWLIST; всё остальное к запуску не допускается

    Env allowlist

    Разрешаются только явно допустимые env-переменные: PATH, LANG, LC_ALL, HOME, PWD, TERM, USER, OPENCLAW_SHELL

    Отключённая сеть

    По умолчанию NETWORK_ENABLED=false — из сессии нет сетевого доступа

    Лимиты процесса

    Память, число процессов, доля CPU и rlimit задаются на сессию отдельными параметрами

    File quota

    Ограничивается размер одного файла

    Session quota

    Ограничивается суммарный объём файлов сессии

    Exec timeout

    Ограничивается длительность выполнения команды

    Output limit

    Ограничивается объём stdout/stderr

    Скрытие host paths

    Клиент не получает внутренние пути хоста

    3.1 Рабочая файловая среда сессии

    Для каждой sandbox-сессии сервис создаёт отдельную рабочую файловую среду.

    Физически рабочая среда размещается под ROOTFS_ROOT. По умолчанию в текущем master это /tmp/workstation/sessions.

    Начальное содержимое рабочей среды формируется из ROOTFS_TEMPLATE_DIR. По умолчанию это /opt/workstation/template.

    По умолчанию /workspace живёт ровно столько, сколько живёт сессия. Отдельной опцией его можно сохранять между сессиями в объектном хранилище S3 — по умолчанию она выключена, описание вынесено на отдельную страницу «[AEF Workstation] S3 долговременное хранение артефактов сессии агента».

    Клиент не получает host path рабочей среды через API. Клиент работает только с виртуальными путями внутри сессии.

    Виртуальный путь

    Назначение

    /

    Корень рабочей среды конкретной sandbox-сессии

    /workspace

    Рабочая директория по умолчанию для файлов проекта и выполнения команд

    Все пути в file API и exec API интерпретируются относительно рабочей среды текущей сессии. Путь не должен выходить за пределы рабочей среды.

    3.2 Режимы изоляции

    Сервис поддерживает несколько runtime-режимов изоляции сессий и файлов. Runtime-режим выбирается конфигурацией сервиса. Клиент не выбирает runtime напрямую в запросе.

    Runtime mode

    Описание

    Статус

    local

    Кастомная изоляция (см. пункт "Алгорим изоляции")

    Используется по умолчанию

    bwrap

    Целевой runtime-режим через systemd-run --user --scope -- bwrap

    Реализован, включается RUNTIME_MODE=bwrap; при отсутствии бинаря bwrap создание сессии завершается ошибкой

    Параметр

    Тип данных

    Значение по умолчанию

    Возможные значения

    Описание

    SESSION_IDLE_TIMEOUT_SEC

    integer

    900 секунд / 15 минут

    Системно задаётся целым числом в секундах, > 0. Бизнес-требованиями не ограничено, техническое максимальное значение: 2 147 483 647 секунд.

    Определяет, сколько сессия может оставаться без операций. Если за это время по сессии нет действий, она считается неактивной и может быть завершена очисткой.

    SESSION_ABSOLUTE_TTL_SEC

    integer

    3600 секунд / 60 минут

    Системно задаётся целым числом в секундах, > 0. Бизнес-требованиями не ограничено, техническое максимальное значение: 2 147 483 647 секунд.

    Определяет максимальное время жизни сессии с момента создания, даже если сессия активно используется.

    CLEANUP_INTERVAL_SEC

    integer

    60 секунд / 1 минута

    Системно задаётся целым числом в секундах, > 0. Бизнес-требованиями не ограничено, техническое максимальное значение: 2 147 483 647 секунд.

    Определяет, как часто сервис проверяет и очищает истёкшие сессии.
