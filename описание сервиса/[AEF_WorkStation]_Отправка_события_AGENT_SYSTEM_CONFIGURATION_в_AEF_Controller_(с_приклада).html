    Функциональное решение

    1. Необходимо отправлять событие AGENT_SYSTEM_CONFIGURATION с приклада AEF Workstation (pod) (указано правило на уровне кода) в топик system.events_<HUB> в ФП AEF Controller соответствующего хаба.:

      1. При каждом старте приложения при каждом старте приложения config-type ="aef-workstation-start"; ;

      2. При каждом создании сессии (sandbox сессии) config-type =" aef-workstation-create-session "; ;

      3. При каждом завершении сессии (sandbox сессии) config-type =" aef-workstation-delete-session "; ;

    2. В случае отсутствия значения обязательного/необязательного параметра в сообщении, отправлять параметр незаполненным (пустым) и продолжать работу приложения.

      aef-workstation

      наличие подключенной AEF WorkStation

      • true - рабочая станция подключена

      • false - рабочая станция НЕ подключена

      да

      boolean (true/false)

      true

      Основной источник OpenClaw json (находится в configMap)

      Пример формирования

      • aef-workstation показывает не фактическую сетевую доступность Workstation, а то, что агент сконфигурирован для работы через Workstation.

        • То есть при старте мы не делаем HTTP-запрос в Workstation и не проверяем /readyz. Мы смотрим только на конфигурацию OpenClaw.

      • aef-workstation=true, если одновременно выполняются условия:

        • Выбран sandbox backend workstation

          • В конфигурации агента sandbox должен быть настроен на использование Workstation как backend.

        • Plugins в OpenClaw включены

          • Общий механизм plugins должен быть активен, иначе workstation plugin не сможет работать.

        • Workstation plugin включен

          • Сам plugin workstation должен быть доступен и не отключен в конфигурации.

        • registerSandboxBackend не отключен

          • У workstation plugin есть настройка регистрации sandbox backend. Если она явно выставлена в false, значит Workstation не должна регистрироваться как backend.

        • Есть endpoint Workstation

          • В конфигурации должен быть endpoint Workstation, либо должен использоваться default endpoint.

        • Конфигурация Workstation валидна

          • Настройки workstation plugin должны корректно разбираться. Если конфиг сломан или имеет неподходящий формат, считаем Workstation неподключенной.

      • Если все эти условия выполнены, в payload отправляем:

        • "aef-workstation": true

      • Если хотя бы одно условие не выполнено, отправляем:

        • "aef-workstation": false

      Важно: true здесь означает “AEFClaw настроен на работу через Workstation”, а не “мы успешно достучались до живого Workstation-сервиса”. Это сделано специально, чтобы startup-сообщение было быстрым и не могло зависнуть из-за сетевой проверки.

      Логика формирования

      • AEFClaw формирует list-tools не из одного файла, а собирает доступные tools на момент старта из нескольких источников.

        • Core / built-in tools

          • Встроенные инструменты OpenClaw. Это базовые возможности агента: работа с файлами, выполнение команд, редактирование, чтение, процессы и другие штатные действия.

        • Sandbox tools

          • Tools, связанные с sandbox-окружением. Они появляются, если для агента настроен sandbox/backend. Например, инструменты для безопасной работы с файлами или выполнения команд внутри изолированной среды.

        • OpenClaw application tools

          • Инструменты самого OpenClaw как приложения: работа с canvas/nodes/browser/media/pdf/image и похожими возможностями, если они доступны в текущей конфигурации.

        • Plugin tools

          • Tools, которые регистрируют plugins. Если plugin установлен, включен и прошел условия загрузки, его инструменты добавляются в общий список доступных tools.

        • Channel tools

          • Tools, которые добавляют каналы связи. Например, channel plugin может дать инструмент для login/action/отправки сообщений или других channel-specific действий.

        • Tools с учетом config/policy

          • После сбора OpenClaw применяет настройки конфигурации: профили tools, allowlist/denylist, ограничения модели, agent-specific настройки и другие политики доступности.

      • Для AEF-сообщения мы берем именно итоговый effective список: то есть не “все теоретически существующие tools”, а те, которые OpenClaw считает доступными для default agent на момент старта.

      • Важный нюанс: на момент старта еще нет активной пользовательской сессии и конкретного канала. Поэтому список строится в startup/default-agent контексте. Мы используем senderIsOwner=true, то есть берем максимально доступный для владельца snapshot. Если позже понадобится более строгий список, это можно будет изменить на senderIsOwner=false.

      В list-tools для каждого tool отправляем:

      - tool-name — техническое имя tool;
      - tool-version — сейчас пустая строка, если версию явно не можем определить;
      - description — описание tool.

      Если доступных tools нет, отправляем пустой массив:

      "list-tools": []

      Если при сборе tools произошла ошибка, Kafka-сообщение все равно отправляется, list-tools будет пустым, а ошибка уйдет в diagnostics и логи.

      Логика формирования

      • AEFClaw ищет skills в нескольких источниках:

      • Дополнительные директории из skills.load.extraDirs
        Пути, которые явно указаны в конфигурации. Это нужно, если skills лежат во внешней папке и их не хотят копировать в проект.

      • Skills, которые поставляют plugins

        • Некоторые plugins могут добавлять свои skills вместе со своей функциональностью. Такие skills появляются, когда соответствующий plugin установлен и включен.

      • Bundled skills, встроенные в OpenClaw

        • Skills, которые поставляются вместе с самим OpenClaw. Это базовый набор, доступный “из коробки”, если он не отключен настройками.

      • Managed skills из пользовательской директории OpenClaw

        • Skills, которыми управляет сам OpenClaw в своей пользовательской директории. Обычно это установленные или синхронизированные skills, доступные для пользователя независимо от конкретного проекта.

      • Personal agents skills из домашней директории пользователя

        • Личные skills пользователя. Они живут вне проекта и могут применяться в разных workspace как персональный набор возможностей/инструкций.

      • Project agents skills из .agents/skills внутри проекта

        • Skills, которые лежат прямо в репозитории/проекте. Они нужны, чтобы проект мог поставлять свои собственные правила, инструкции или возможности для агента

      • Workspace skills из директории skills внутри workspace

        • Skills, привязанные к конкретному workspace агента. Это самый близкий к текущему запуску источник, поэтому он может переопределять более общие skills с тем же именем.
