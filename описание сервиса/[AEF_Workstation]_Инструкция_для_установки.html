    Инструкция для разворачивания AEF Workstation


    Workstation с точки зрения cicd является не стандартным агентом, поэтому запуск его сборки происходит через Dockerfile указанный в дистрибутиве. Но при этом, он также использует стандартные конфигурации.

    Отсюда, в файле агента должно быть следующее:


    agents.yaml
    - AGENT_NAME: workstation
    ENV:
    # Workstation database
    DATABASE_URL: 'sqlite+aiosqlite:////tmp/workstation.db'
    # Optional: list of DBs for master auto-selection
    DATABASE_AUTO_MASTER: 'false'
     
    # Workstation session
    SESSION_PROFILE: 'default'
     
    # Memory limit for sandbox processes (bytes)
    MEMORY_LIMIT_BYTES: '536870912'
     
    # Workstation runtime
    RUNTIME_MODE: 'local'
    LOG_LEVEL: 'INFO'
    HOST: '127.0.0.1'
    PORT: '8080'

    [Временно] AEF Workstation в кластере AEF (вызов по API)

    Данный вариант доступен только на ИФТ как временное решение. Целевым решением является установка AEF WorkStation в кластер Агента.


    Для быстрого подключения и тестирования гипотез AEF Workstation развернут в кластере AEF в доступен по API.

    HOST: workstation.dev0.apps.azwx5oj1.k8s.delta.sbrf.ru

    API

    /v1/sessions

    Все ручки кроме создания требуют заголовки Authorization: Bearer <token> и X-Session-Id.

    • POST /v1/sessions — создать сессию (идемпотентно по X-Session-Id). Возвращает token и состояние. 201 при создании, 200 если уже существует.

    • GET /v1/sessions/{id} — прочитать состояние сессии.

    • POST /v1/sessions/{id}:terminate — завершить сессию (terminating → terminated, удаляет rootfs).

    • POST /v1/sessions/{id}/exec — выполнить команду синхронно, вернуть stdout, stderr, rc.

    • POST /v1/sessions/{id}/exec:stream — то же самое, но NDJSON-стрим событий stdout/stderr/rc.

    • POST /v1/sessions/{id}/files:upload — загрузить файл в rootfs (multipart).

    • POST /v1/sessions/{id}/files:download — скачать файл из rootfs (binary + заголовки X-File-Sha256, X-File-Bytes).

    • POST /v1/sessions/{id}/files:list — список файлов и директорий в rootfs.


    Жизненный цикл сессии

    Состояния SessionStatus:

    • provisioning — rootfs ещё создаётся.

    • ready — готова принимать exec и file-операции.

    • terminating — инициировано завершение.

    • terminated — завершена, rootfs удалён.

    • failed — не удалось создать rootfs или runtime недоступен.


    Переходы:

    • provisioning → ready → terminating → terminated

    • provisioning → failed

    • ready → failed


    Типичный сценарий создания и использования сессии

    • Клиент делает POST /v1/sessions с заголовком X-Session-Id: sess.

    • SessionService создаёт запись в БД со статусом provisioning.

    • Создаёт директорию ROOTFS_ROOT/sess/rootfs.

    • Копирует busybox-шаблон в rootfs.

    • Обновляет статус на ready.

    • API отвечает 201 с токеном и состоянием.

    • Клиент делает POST /v1/sessions/sess/exec с Bearer <token>.

    • SessionService вызывает RuntimeAdapter.exec, который запускает команду через chroot или bwrap внутри rootfs.

    • API возвращает ExecResponse с rc, stdout, stderr.

    • Клиент может загрузить или скачать файлы через /files:upload и /files:download. Проверяется MAX_FILE_SIZE.

    • Клиент делает POST /v1/sessions/sess:terminate.

    • SessionService переводит статус в terminating, удаляет rootfs, переводит в terminated.

    • API возвращает SessionTerminateResponse.


    Фоновые задачи

    PeriodicTasks._cleanup_sessions — запускается раз в CLEANUP_INTERVAL_SEC (по умолчанию 60 секунд):

    • Завершает сессии с истёкшим SESSION_IDLE_TIMEOUT_SEC или SESSION_ABSOLUTE_TTL_SEC.

    • Переводит их в terminating → terminated, удаляет rootfs.
