    1. Описание сервиса

    AEF WorkStation предназначен для предоставления AI-агенту безопасной, изолированной рабочей среды, в которой можно выполнять команды, запускать код и работать с файлами.

    Агент не управляет runtime-механизмами напрямую и не работает с файловой системой хоста. Взаимодействие клиента с AEF WorkStation выполняется только через REST API.

    2. Управление сессиями

    Sandbox-сессия — основная сущность работы сервиса. Это изолированная рабочая среда, связанная с конкретным X-Session-Id. В рамках одной sandbox-сессии сохраняются загруженные файлы, результаты предыдущих операций и служебное состояние. Разные sandbox-сессии не имеют доступа к файлам и состоянию друг друга.

    Клиенту достаточно знать три вещи:

    Сущность

    Зачем нужна

    session_id

    Идентифицирует sandbox-сессию

    token

    Подтверждает право выполнять операции в рамках сессии

    REST API

    Даёт единый способ создавать среду, выполнять команды и работать с файлами

    AEF WorkStation самостоятельно отвечает за создание рабочей среды, запуск команд, контроль ограничений, продление активности и очистку ресурсов.

    Виртуальный путь

    Назначение

    /

    Корень рабочей среды конкретной sandbox-сессии; используется по умолчанию в exec и files:list

    /workspace

    Рабочая директория для файлов проекта; единственный каталог, который может сохраняться между сессиями через опцию S3

    Все пути в file API и exec API интерпретируются относительно рабочей среды текущей сессии. Путь не должен выходить за пределы рабочей среды.

    2.1 Создание sandbox-сессии (POST /v1/sessions)

    Sandbox-сессия скрывает от клиента детали создания рабочей среды. Клиент получает только публичные атрибуты сессии и token для дальнейших операций.

    Для начала работы клиент вызывает POST /v1/sessions. Метод создаёт новую sandbox-сессию или переиспользует уже готовую сессию с тем же X-Session-Id.

    X-Session-Create-Secret

    0..1

    string

    Общий секрет вызывающей стороны. Обязателен, если на сервисе включён IS_CREATE_SESSION_SECRET; иначе не проверяется

    Content-Type

    idleTimeoutSec

    0..1

    integer/null

    Время жизни без активности; не может превышать системный лимит

    absoluteTtlSec

    0..1

    integer/null

    Максимальное время жизни независимо от активности; не может превышать системный лимит

    0..1

    object/null

    Используется для S3. Запрос восстановления долговременного /workspace из объектного хранилища. Если не передан, обмена с S3 не происходит и /workspace стартует пустым

    workspacePersistence.scopeId

    1..1

    string

    Используется для S3. Адрес ячейки хранения, 1–128 символов. Не должен содержать сырой пользовательский sessionKey

    workspacePersistence.root

    0..1

    string

    Используется для S3. Единственное допустимое значение — /workspace; оно же по умолчанию

      "idleTimeoutSec": 1800,
      "absoluteTtlSec": 7200,
      "workspacePersistence": {
        "scopeId": "3c8f9f4d8b6a",
        "root": "/workspace"
      }
    }

    Логика выполнения

    Состояние сессии

    Поведение сервиса

    Сессия отсутствует

    Создаётся новая запись состояния, генерируется token, подготавливается рабочая среда, сессия переводится в ready

    Сессия существует в ready

    Сервис переиспользует существующую среду, новый token не возвращает

    Сессия в provisioning или terminating

    Сервис возвращает ошибку текущего состояния

    Сессия в terminated или failed

    Сервис пересоздаёт среду для того же X-Session-Id и выдаёт новый token

    Создание по одному X-Session-Id сериализуется: параллельные вызовы обрабатываются по очереди. Если передан workspacePersistence, восстановление /workspace выполняется синхронно до перехода в ready, и его ошибка переводит сессию в failed.

    2.4 Продление активности сессии

    При успешных рабочих операциях сервис обновляет активность сессии. Активностью считаются:

    Операция

    Продлевает активность

    Получение сведений о ready-сессии

    Да

    exec

    Да

    exec:stream

    Да

    files:upload

    Да

    files:download

    Да

    files:list

    Да

    Срок истечения рассчитывается с учётом idleTimeoutSec и absoluteTtlSec. Сессия не может жить дольше absolute TTL. Если активности нет дольше idle TTL, сессия считается просроченной.

    Запись отметки активности в базу дебаунсится на SESSION_TOUCH_DEBOUNCE_SEC (по умолчанию 5 секунд): на серии частых вызовов expiresAt может отставать на этот интервал.

    6. Логирование

    Сервис пишет структурированные логи в двух представлениях: человекочитаемая строка в stdout и JSON в формате ECS в файл APP_LOG_DIR/app.log, который забирает fluentbit. Ниже приводится JSON-представление, потому что именно оно попадает в систему сбора логов. Каждая запись — одна строка.

    Уровень задаётся APP_LOG_LEVEL (по умолчанию INFO) и отдельно APP_LOG_LEVEL_CORE для кода самого сервиса. При INFO записи уровня DEBUG не пишутся.

    Уровень

    Когда используется

    DEBUG

    Приём запроса и начало каждой операции: фиксируется факт вызова до результата

    INFO

    Успешное завершение операции, а также штатные пропуски: переиспользование сессии, повторный terminate, пропуск занятой сессии при очистке

    ERROR

    Любая неуспешная операция: с типом ошибки, сообщением и stack trace

    WARNING

    Только на уровне окружения, не на запросах: недоступный на запись каталог логов, включённое хранилище /workspace при SQLite-базе

    CRITICAL

    Не используется

    Секреты вычищаются перед записью: значения ключей authorization, token, secret, password, api_key и подобных заменяются на [redacted], строки длиннее 4096 символов и массивы длиннее 50 элементов обрезаются.

    Общие поля всех записей — в примерах ниже они опущены, чтобы не дублировать: @timestamp, log.level, message, service.name, app.request_id (из X-Request-Id или сгенерированный), trace.id, span.id, app.agent_id, kubernetes.pod.name. У записей уровня ERROR дополнительно присутствуют error.type, error.message, error.stack_trace.
