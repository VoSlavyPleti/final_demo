# Сопоставление договора с банковской матрицей

## Цель и границы

Прочитать `/inputs/contract.txt` и `/inputs/matrix.json`, построить единую карту
юридических аналогов и сохранить её в `/outputs/working/mapping.json`.

На этом этапе не определять применимость, не присваивать статусы, не оценивать риск и не
формировать заключение. Отличие в роли, сроке, сумме, объёме, условии или способе исполнения
не уничтожает существующий юридический аналог: такие отличия оцениваются на следующем этапе.

Перед сопоставлением использовать примеры из `references/mapping-examples.md` как границы
между прямым аналогом, допустимой инверсией и слабым тематическим совпадением.

## Единица анализа

- Один исходный нумерованный пункт договора является одной contract-oriented группой,
  независимо от количества содержащихся в нём положений.
- Создавать группу для каждого нумерованного пункта с самостоятельным юридическим
  содержанием, в том числе для пункта без аналога. Не создавать группы для заголовков,
  реквизитов и определений, которые сами не устанавливают право, обязанность, ограничение
  или ответственность.
- Один пункт договора может быть связан с несколькими пунктами матрицы. Один пункт матрицы
  может использоваться в нескольких группах. Связи не являются взаимоисключающими.
- Сначала установить по преамбуле, предмету и оперативным положениям алиасы `Банка` и
  `Предприятия`. Названия `Заказчик` и `Исполнитель` сами по себе роли не доказывают.

## Правило юридического аналога

Сопоставлять по регулируемому правоотношению и правовому эффекту. Проверять сторону,
действие или право, объект, адресата, основание, триггер, механизм и результат.

1. Сначала искать прямой аналог во всём договоре или во всей матрице. Прямой аналог
   регулирует то же действие, право или обязанность в том же правоотношении. Изменённый
   срок, сумма, условие, объём либо триггер не мешает принять такую связь.
2. Если прямого аналога конкретному положению нет, искать допустимую инверсию: корреспондирующее
   действие другой стороны в том же процессе, с тем же объектом и сопоставимым правовым
   результатом. Инверсия является fallback-кандидатом, а не равной альтернативой прямому
   аналогу. Если прямой кандидат найден, инверсию для замены этого кандидата не добавлять.
3. Не принимать связь по одному номеру, общей теме, совпавшим словам, одинаковой стороне,
   одинаковому сроку либо упоминанию одного продукта. Действие, объект или юридический
   результат из другого правоотношения аналогом не являются.
4. Положение договора может покрываться совокупностью пунктов матрицы, а положение матрицы —
   совокупностью пунктов договора. Каждый принятый кандидат должен подтверждать конкретную
   часть исходного нумерованного пункта.

## Contract-oriented карта и mapped scope

Для каждой группы сначала выбрать все `matrix_ids`, затем для каждого выбранного ID создать
ровно один объект `mapped_scope`:

- `contract_scope` — краткое, близкое к источнику описание реально выраженного аспекта
  текущего пункта договора, включая принадлежащее ему ненумерованное продолжение;
- `matrix_scope` — краткое, близкое к источнику описание соответствующего аспекта именно
  выбранного пункта матрицы.

Не переносить содержание из соседнего, родительского или дочернего пункта, если оно не
включено прямой ссылкой. Не дополнять источник подразумеваемым правилом и не изобретать
действие, условие, срок, сумму или правовой эффект. При прямой ссылке фиксировать саму
ссылку и только прямо включённый ею смысл.

Порядок и состав `mapped_scope[].matrix_id` должны точно совпадать с `matrix_ids`. Если
`matrix_ids` пуст, `mapped_scope` также пуст.

## Исчерпывающая обратная проверка матрицы

После contract-oriented поиска обработать каждый исходный объект массива
`/inputs/matrix.json` ровно один раз и в исходном порядке.

- Не определять применимость и не фильтровать по `required_type`, продуктовым, закупочным,
  платёжным, терминальным или иным селекторам. Проверять все строки, включая структурные.
- Для каждого пункта матрицы проверить весь договор: сначала прямые аналоги, затем — только
  при их отсутствии — допустимые инверсии.
- Обнаруженную связь добавить в соответствующую contract-oriented группу, а не создавать
  вторую matrix-oriented карту. Все связи хранятся один раз в `mappings`.
- Внести ID в `missing_matrix_ids`, только если после обратной проверки у него нет ни одного
  принятого аналога. Это означает лишь отсутствие связи и ещё не означает юридический статус,
  применимость, обязательность или риск.

## Формат рабочего артефакта

Сохранить чистый валидный JSON без Markdown и постороннего текста:

```json
{
  "completion_status": "complete",
  "mappings": [
    {
      "contract_id": "1.1",
      "contract_locator": "Основной текст, п. 1.1",
      "matrix_ids": ["2.1", "2.4"],
      "mapped_scope": [
        {
          "matrix_id": "2.1",
          "contract_scope": "аспект, подтверждённый пунктом договора",
          "matrix_scope": "соответствующий аспект пункта матрицы"
        },
        {
          "matrix_id": "2.4",
          "contract_scope": "другой подтверждённый аспект договора",
          "matrix_scope": "соответствующий аспект другого пункта матрицы"
        }
      ]
    }
  ],
  "missing_matrix_ids": ["2.5"]
}
```

Не добавлять статусы, оценки, комментарии, уверенность или иные поля.

## Самопроверка

Перед завершением повторно сверить каждую принятую связь с точными исходными пунктами и
проверить:

- каждой связи соответствует подтверждённое содержание обоих источников;
- прямая связь имеет приоритет перед инверсией, а слабая тематическая связь отклонена;
- `matrix_ids` совпадают по порядку и составу с `mapped_scope[].matrix_id`;
- `missing_matrix_ids` содержит только уникальные исходные ID в порядке матрицы;
- использованные в `mappings` ID не пересекаются с `missing_matrix_ids`;
- объединение mapped и missing ID равно всем уникальным `number` из матрицы.

Установить `completion_status: "complete"` только после выполнения всех проверок.
