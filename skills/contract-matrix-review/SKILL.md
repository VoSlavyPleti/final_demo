# Проверка договора по банковской матрице

## Назначение

Провести полный анализ текущего договора относительно применимых требований банковской матрицы, построить внутреннюю карту покрытия и сохранить итоговое заключение только о выявленных расхождениях.

## Входы

- `/inputs/contract.txt` — полный текст текущего договора с сохранёнными исходными номерами пунктов, таблицами и приложениями.
- `/inputs/matrix.json` — действующая банковская матрица с исходными идентификаторами и текстом её пунктов.

## Режим исполнения: проверить до первой записи

Сначала определить свой режим. Главный агент получил исходное задание на полный анализ. Делегированный сабагент запущен вызывающим агентом через `task`; это также подтверждается системным сообщением о том, что вызывающий агент увидит только его финальный ответ, либо заданием, ограниченным частью матрицы.

В делегированном режиме все упоминания канонических `/outputs/working/analysis.json`, `/outputs/result.json`, глобального reverse pass и завершения анализа в последующих разделах относятся только к главному агенту. Делегированный сабагент их не создаёт, не изменяет и не удаляет. Он выполняет для точного списка `assigned_matrix_ids` только этапы проверки входов, применимости и matrix-oriented сопоставления, затем локально проверяет полноту своей области.

Результат делегированной области сохраняется в уникальный `/outputs/working/subagents/<scope>.json`, указанный в задании. Если вызывающий агент не указал путь, сформировать `<scope>` из назначенного раздела матрицы латиницей и с подчёркиваниями; путь всё равно должен находиться только в каталоге `subagents`. Сохранить объект `{"scope": "<scope>", "assigned_matrix_ids": [...], "groups": [...]}` без `completion_status`, общего профиля, `contract_inventory`, `extra_in_contract` и итогового заключения. После повторного чтения этого файла вернуть вызывающему агенту его путь, область и число групп.

## Рабочее состояние

В главном режиме в ходе одного непрерывного анализа поддерживай `/outputs/working/analysis.json` как каноническое рабочее состояние текущего запуска. Фиксируй в нём:

- профиль договора и алиасы сторон;
- карту связи приложений и таблиц с исходными нумерованными пунктами `source_anchor_map`;
- решение о применимости каждого пункта матрицы;
- matrix-oriented группы с найденными аналогами, охваченным содержанием и внутренним статусом;
- компактный `contract_inventory` с покрытым и остаточным юридически значимым содержанием каждого исходного пункта договора;
- состояние проверки полноты анализа.

Сопоставление и статус фиксируются совместно в одной группе как взаимосвязанные выводы. Полностью согласованные группы сохраняются в рабочем состоянии для подтверждения покрытия, но не переносятся в итоговое заключение.

Рабочее состояние не является заключением. Итоговый артефакт с выявленными разногласиями сохраняется в `/outputs/result.json`.

## Калибровка решений

До определения применимости и начала сопоставления полностью прочитать `references/calibration.md`. Использовать содержащиеся в нём проверенные примеры и антипримеры как обязательную калибровку границ юридического аналога и статусов.

Для каждого решения о применимости, каждой matrix-oriented группы и каждого кандидата на `extra_in_contract` выполнить сверку с reference. При наличии материально сходного примера выбрать один или несколько `case_id` и зафиксировать их в поле `calibration_case_ids` рабочего состояния. При совпадении решающих фактов применять тот же принцип классификации. Отступать от результата примера только при наличии юридически значимого отличия текущих источников и фиксировать это отличие в рабочем состоянии.

Если материально сходного примера нет, установить `calibration_case_ids: ["no_materially_similar_case"]` и применить прямые правила `AGENTS.md`. Не притягивать пример только ради заполнения поля.

Поле `calibration_case_ids` используется только для внутренней самопроверки: в главном режиме сохраняется в `/outputs/working/analysis.json`, а в делегированном — в назначенном файле области. В `/outputs/result.json` оно не переносится.

Не переносить из reference идентификаторы, стороны, применимость или готовые выводы в текущий анализ. Использовать его только для калибровки способа сравнения; факты устанавливать по текущим входам. При противоречии приоритет имеют `AGENTS.md`, текущая матрица и текущий договор.

Перед формированием итогового артефакта повторно проверить каждую выводимую группу по связанным `calibration_case_ids` либо, при значении `no_materially_similar_case`, непосредственно по применённым правилам `AGENTS.md`.

## Делегирование частей анализа

Навык применяется в одном из двух режимов:

- главный агент выполняет исходное задание целиком, координирует делегирование, ведёт каноническое рабочее состояние и формирует заключение;
- делегированный сабагент получает в задании точную область матрицы и уникальный рабочий файл `/outputs/working/subagents/<scope>.json`, анализирует только эту область и возвращает материал главному агенту.

Если часть анализа передаётся сабагенту, в каждое задание явно включить требование до содержательной работы прочитать `/AGENTS.md`, загрузить и полностью выполнить `/skills/contract-matrix-review/SKILL.md`, а также полностью прочитать `/skills/contract-matrix-review/references/calibration.md`. Однозначно указать делегированный режим, точный упорядоченный список `assigned_matrix_ids` и уникальный рабочий файл. Для каждого назначенного пункта матрицы потребовать ровно одну matrix-oriented группу и один статус.

Делегированный сабагент сохраняет в назначенный файл объект вида `{"scope": "<scope>", "assigned_matrix_ids": [...], "groups": [...]}`. Каждая группа содержит `matrix_id`, применимость, `required_type`, статус, `accepted_contract_items`, `uncovered_or_changed_elements`, `rejected_weak_candidates`, `calibration_case_ids` и краткий комментарий. В принятых договорных кандидатах сохраняются исходные ID, локаторы и `mapped_scope`, но полные исходные тексты для всех рабочих групп не дублируются. В файле отсутствуют `completion_status` и итоговое заключение. Назначенный файл является единственным артефактом задания; глобальную остаточную проверку договора, проверку полноты всего анализа и публикацию заключения выполняет главный агент после получения всех областей. Канонические `/outputs/working/analysis.json` и `/outputs/result.json` ведёт только главный агент.

Делегированный сабагент завершает область только после проверки точного равенства мультимножеств `assigned_matrix_ids` и `groups[].matrix_id`: ни один ID не пропущен и не повторён.

Главный агент дожидается завершения всех назначенных задач, перечитывает каждый уникальный файл и проверяет, что списки `assigned_matrix_ids` не пересекаются и совместно содержат по одной группе для каждого исходного пункта матрицы. До включения результата в каноническое рабочее состояние главный агент обязан перепроверить каждую полученную группу по исходному пункту матрицы, договорным доказательствам, правилам `AGENTS.md` и связанным калибровочным примерам. Материал сабагента не является авторитетным источником и не переносится в итоговый артефакт без такой проверки.

## Порядок анализа

### 1. Проверить входы и зафиксировать контекст договора

Полностью прочитать договор и матрицу до формирования выводов. Убедиться, что доступны все исходные нумерованные пункты, таблицы и приложения, а у каждой строки матрицы сохранены исходный идентификатор и текст. При невозможности полного чтения прекратить анализ по правилу из `AGENTS.md` и не создавать итоговое заключение.

Зафиксировать в `contract_profile` рабочего состояния:

- предмет и вид договора;
- наименование Банка в договоре и используемые для него алиасы;
- наименование контрагента и его алиасы;
- роли иных участников, если они влияют на обязательства;
- прямо указанный правовой или закупочный режим;
- характеристики договора, от которых зависит применимость требований матрицы;
- включённые в договор таблицы и приложения, а также пункты, которые на них ссылаются.

Подтверждать элементы профиля ссылками на исходные пункты договора. Не включать в профиль сведения, которые не влияют на применимость требований или юридическое сопоставление.

Для каждого приложения и каждой таблицы отдельно зафиксировать в `source_anchor_map`, связаны ли они с нумерованным пунктом договора. Для связанного источника сохранить `anchor_contract_id`, локатор ссылки и точный локатор материала. Для непривязанного источника сохранить существующий заголовок либо точное описание расположения без изобретения ID. До использования пустого ID повторно проверить отсутствие прямой и общей ссылки из номерных пунктов договора.

### 2. Определить применимость каждого пункта матрицы

Для каждого пункта матрицы сопоставить условия его применимости с подтверждённым профилем договора. Использовать поля `only_for_product`, `only_for_lot`, `payment_method` и `only_for_terminal`, а также прямо выраженное содержание пункта матрицы.

Считать значения внутри одного поля применимости альтернативами, а разные непустые поля — совокупными условиями. Например, пункт с `only_for_product: ["trade_acquiring"]` и `payment_method: ["qr"]` применим при одновременном наличии торгового эквайринга и оплаты по QR-коду.

Для каждой исходной строки матрицы сразу создать одну рабочую matrix-oriented группу. Для применимого пункта зафиксировать решение `applicable` и передать эту же группу на сопоставление в следующий этап. Для неприменимого пункта установить внутренний статус `not_applicable`, оставить договорную сторону группы пустой и прекратить дальнейший анализ этой группы. Группы `not_applicable` нужны только для учёта полноты и в итоговое заключение не переносятся.

Зафиксировать для каждого рабочего пункта:

- решение `applicable` или `not_applicable`;
- краткое основание;
- подтверждающие пункты договора либо элементы `contract_profile`;
- исходный признак `mandatory` или `optional`.

Присваивать `not_applicable` только при наличии подтверждённого несоответствия условиям применимости. Отсутствие аналога в договоре не является доказательством неприменимости. При недостаточности сведений считать пункт применимым.

Пункт с незаполненным `required_type` является структурным заголовком, а не самостоятельным требованием. Учитывать его как контекст со статусом `not_applicable` и не использовать его отсутствие для формирования `missing_in_contract`.

### 3. Сопоставить каждый применимый пункт матрицы и определить статус

Для каждой применимой matrix-oriented группы, созданной на предыдущем этапе, выполнить сопоставление и определить итоговый статус, не создавая второй группы для того же якорного пункта. Искать по всему договору пункты, регулирующие ту же юридическую операцию, обязанность, право, ограничение или правовое последствие. Допускать включение одного пункта договора в несколько разных matrix-oriented групп.

Сначала отдельно решить, является ли каждый кандидат принятым юридическим аналогом. Принять кандидат, если он регулирует ту же основную юридическую операцию и совпадает хотя бы её основное действие либо юридический механизм с относящимся к этой операции запускающим событием, даже когда покрывает только часть составного требования. Различие стороны, объекта, получателя, объёма, условия, срока или суммы учитывать при последующей оценке покрытия, пока сохраняется эта общая операция. Одинаковый конечный результат при другом действии, механизме или основании сам по себе аналог не образует. Отклонить кандидат как слабый, если совпадает только результат, тема, продукт, техническая возможность или лексика. Для каждого принятого аналога зафиксировать относящееся к якорному требованию содержание в `mapped_scope`; для значимого отклонённого слабого кандидата кратко зафиксировать причину отклонения.

После нахождения кандидатов выделить внутри якорного пункта матрицы только необходимые для проверки элементы: обязанную сторону, действие, объект, адресата или выгодоприобретателя, объём, условия, исключения, последствия, сроки и суммы. Проверить их совокупное покрытие всеми принятыми договорными аналогами.

Засчитывать покрытие каждого элемента только в пределах того же регулируемого отношения. Срок, сумма, условие или иное положение договора покрывает элемент матрицы лишь тогда, когда непосредственно относится к сопоставляемой обязанности, праву или операции либо связано с ними действующей перекрёстной ссылкой. Наличие в договоре любого пункта с похожим сроком, суммой или формулировкой, относящегося к другому обязательству, покрытием не является.

Если часть требования не покрыта, продолжить целевой поиск дополнительного аналога, включая перекрёстные ссылки, приложения, допустимые ссылки на закон и инвертированные взаимные обязательства. Не присваивать итоговый статус, пока сохраняется разумная возможность покрытия непроверенного элемента другим пунктом договора.

Перед присвоением `missing_in_contract` или `optional_absent` попытаться опровергнуть отсутствие: повторно проверить основной текст, связанные приложения и таблицы, перекрёстные ссылки, тот же механизм в иной редакции, сильные частичные аналоги и допустимую инверсию. Точный либо частичный аналог в связанном приложении учитывается наравне с основным текстом и относится к исходному нумерованному якорю согласно `source_anchor_map`.

После полного покрытия прекратить поиск дополнительных подтверждающих кандидатов, но проверить, не изменяет ли другой прямо связанный пункт договора то же требование, в частности посредством исключения, ограничения, специального условия, иного срока или иной суммы.

Присвоить группе один статус:

- `aligned` — все элементы якорного требования совокупно покрыты без изменения юридического содержания;
- `deviation` — найден хотя бы один юридический аналог, но требование покрыто не полностью, изменено, ограничено, инвертировано или ему противоречит связанное условие договора;
- `missing_in_contract` — для применимого обязательного требования не найден ни один принятый юридический аналог;
- `optional_absent` — для применимого необязательного требования не найден юридический аналог.

Оценивать только содержание, относящееся к якорному пункту матрицы. Содержание того же договорного пункта, относящееся к другим требованиям матрицы, само по себе не является отклонением.

Для каждой применимой рабочей группы сохранить как минимум:

- `accepted_contract_items` — принятые аналоги с исходным ID, локатором и `mapped_scope`;
- `uncovered_or_changed_elements` — непокрытые либо изменённые элементы матричного требования;
- `rejected_weak_candidates` — значимые слабые кандидаты с краткой причиной отклонения, особенно для `missing_in_contract` и `optional_absent`;
- `calibration_case_ids` и краткий комментарий.

Соблюдать инварианты: у `aligned` есть принятый аналог и нет непокрытых или изменённых элементов; у `deviation` есть хотя бы один принятый аналог и конкретное отличие; у `missing_in_contract` и `optional_absent` массив принятых аналогов пуст. Порог принятия кандидата одинаков для обязательных и необязательных требований. Прямой частичный аналог необязательного требования получает `deviation`, а не `optional_absent`.

### 4. Проверить остаточное содержание договора

После построения всех matrix-oriented групп один раз проверить каждый смысловой пункт договора и каждую юридически значимую непривязанную исходную единицу. Использовать зафиксированный `mapped_scope`, чтобы отделить содержание, уже учтённое в matrix-oriented группах, от остаточного содержания. Это остаточная проверка, а не второй полный поиск contract-oriented статусов.

Создать в рабочем состоянии компактный `contract_inventory` с одной записью для каждого исходного смыслового пункта договора и каждой юридически значимой непривязанной единицы. Для каждой записи сохранить исходный ID либо локатор, связанные `mapped_matrix_ids`, покрытый `mapped_scope`, остаточный `residual_scope` и одно решение `disposition`:

- `no_residual` — самостоятельного остатка нет;
- `residual_attached_to_deviation` — остаток изменяет сопоставленное матричное требование и перенесён в соответствующую группу `deviation`;
- `extra` — самостоятельный остаток не имеет принятого матричного аналога и оформлен как `extra_in_contract`;
- `non_substantive` — исходная единица не создаёт самостоятельного юридически значимого условия.

Если всё юридически значимое содержание пункта покрыто принятыми сопоставлениями, не формировать для него contract-oriented группу.

Для каждого остаточного положения сначала определить его связь с уже сопоставленными требованиями:

- если положение изменяет, ограничивает, дополняет условием или иным образом затрагивает принятый аналог матричного требования, отразить его в соответствующей matrix-oriented группе и установить либо сохранить статус `deviation`;
- если положение создаёт отделимое самостоятельное условие, выполнить целевой поиск его юридического аналога в матрице;
- если найден достаточный аналог, дополнить соответствующую matrix-oriented группу и повторно проверить её статус;
- если достаточного аналога нет либо найден только слабый кандидат, сформировать для исходного пункта договора одну contract-oriented группу `extra_in_contract`.

Если пункт договора вообще не участвовал в принятых сопоставлениях, проверить весь пункт по тем же правилам. Формировать `extra_in_contract` только при наличии самостоятельного юридически значимого условия.

Не определять `extra_in_contract` простым вычитанием использованных идентификаторов договора. Один пункт может быть частично покрыт матрицей и одновременно содержать самостоятельный остаток. В комментарии описывать только остаточное условие, а не весь пункт целиком.

Использование ID договора хотя бы в одной matrix-oriented группе не означает покрытия всего его содержания. Не завершать остаточную проверку, пока каждая запись `contract_inventory` не имеет объяснённого `disposition`, а каждый `residual_scope` не перенесён в matrix-oriented `deviation` либо в одну группу `extra_in_contract`.

### 5. Подготовить состав итогового заключения

После завершения matrix-oriented анализа и остаточной проверки договора определить в рабочем состоянии группы, подлежащие переносу в итоговое заключение. На этом этапе не сохранять `/outputs/result.json`: итоговый файл формируется только после проверки полноты на следующем этапе.

Включить в итоговый артефакт только:

- matrix-oriented группы `deviation`;
- matrix-oriented группы `missing_in_contract`;
- contract-oriented группы `extra_in_contract`.

Не включать группы `aligned`, `optional_absent`, `not_applicable` и структурные элементы матрицы. Их сохранить только в рабочем состоянии как подтверждение полноты анализа.

Переносить каждую выявленную группу в заключение без изменения её якоря:

- один пункт матрицы со всеми принятыми договорными аналогами образует одну итоговую строку `deviation` или `missing_in_contract`;
- один исходный пункт договора с самостоятельным остаточным условием образует одну итоговую строку `extra_in_contract`;
- не объединять разные якорные пункты матрицы в одну строку;
- не создавать искусственные идентификаторы для частей пунктов.

Для каждой группы сохранить исходные тексты и идентификаторы связанных пунктов. В комментарии описать только конкретное отсутствие, изменение или самостоятельное остаточное условие. Не добавлять оценку риска, юридические последствия, предлагаемую редакцию или план исправления.

Расположить matrix-oriented разногласия в порядке пунктов матрицы, затем `extra_in_contract` в порядке пунктов договора.

### 6. Проверить полноту и завершить анализ

До сохранения итогового артефакта перечитать рабочее состояние и провести сплошную проверку полноты.

Сверить исходные пункты матрицы с matrix-oriented картой:

- мультимножества исходных ID матрицы, всех `assigned_matrix_ids` и `groups[].matrix_id` канонического рабочего состояния точно равны;
- каждый исходный пункт матрицы представлен ровно одной группой;
- каждая группа имеет решение о применимости и ровно один допустимый статус;
- группы с одинаковым якорным пунктом отсутствуют;
- `aligned` присвоен только при наличии принятого аналога, полном совокупном покрытии требования и пустом `uncovered_or_changed_elements`;
- `deviation` содержит хотя бы один принятый юридический аналог и непустой перечень конкретных непокрытых, изменённых либо противоречащих элементов;
- `missing_in_contract` присвоен только применимому обязательному требованию с пустым массивом принятых аналогов после попытки опровергнуть отсутствие;
- `optional_absent` присвоен только применимому необязательному требованию без аналога;
- `not_applicable` имеет подтверждённое основание неприменимости.

Целевым образом перепроверить потенциально ошибочные границы перед публикацией:

- каждую группу `missing_in_contract` и `optional_absent` — по связанным приложениям, перекрёстным ссылкам, сильным частичным аналогам и инверсии;
- каждую группу `aligned`, в доказательствах которой присутствуют незаполненное поле, прочерк, иной срок или сумма, явное отрицание, исключение либо специальное условие договора;
- каждый применимый optional-пункт, для которого найден прямой либо частичный договорный аналог;
- каждую цепочку самостоятельных обязанностей — не использовано ли условие об одной предпосылке как ложный аналог другого действия.

Сверить исходные пункты договора с результатами остаточной проверки:

- каждый смысловой пункт договора и каждая юридически значимая непривязанная единица представлены ровно одной записью `contract_inventory`;
- каждый смысловой пункт договора и каждая юридически значимая непривязанная исходная единица проверены на остаточное содержание;
- каждый остаток либо учтён как изменение соответствующей matrix-oriented группы, либо сопоставлен с другим пунктом матрицы, либо оформлен как `extra_in_contract`;
- каждая запись имеет одно допустимое и объяснённое `disposition`;
- одно и то же юридически значимое содержание не учтено одновременно как покрытое матрицей и как `extra_in_contract`;
- определения, реквизиты и технические материалы не признаны `extra_in_contract` без самостоятельного юридического условия.

Повторно проверить, что стороны, действия, объекты, условия, исключения, последствия, сроки и суммы сопоставлялись только в рамках относящегося к ним юридического отношения. Убедиться, что изменение срока или суммы не пропущено и не перенесено в несвязанную матричную группу.

После прохождения проверки один раз создать `/outputs/result.json`, затем перечитать сохранённый файл и убедиться, что:

- файл является корректным UTF-8 JSON и соответствует установленной схеме;
- в `disagreements` присутствуют только `deviation`, `missing_in_contract` и `extra_in_contract`;
- состав разногласий полностью совпадает с выводимыми группами рабочего состояния;
- исходные идентификаторы и тексты повторно прочитаны из договора и матрицы, а не скопированы из сокращённого рабочего описания;
- полные тексты перенесены дословно без внесённых многоточий, квадратных сокращений, пересказа, исправлений или нормализации;
- связанный материал приложения или таблицы использует ID исходного нумерованного якоря, а `id: null` оставлен только действительно непривязанному материалу без собственного ID;
- искусственные идентификаторы не созданы;
- поля каждой группы заполнены согласно её статусу;
- комментарий фиксирует конкретное расхождение или остаточное условие без дополнительных юридических выводов.

Установить `completion_status: "complete"` только после успешного прохождения всех проверок. Если повторное чтение выявило ошибку, исправить рабочее состояние и изменить уже существующий `/outputs/result.json` посредством `edit_file`, затем снова перечитать его. Не удалять итоговый файл ради повторного создания и не вызывать `write_file` для пути, который уже существует. То же правило применять к уже созданному `/outputs/working/analysis.json`: последующие изменения вносить через `edit_file`. Если завершить проверку невозможно, применить правило невозможности завершения из `AGENTS.md`.

## Формат итогового артефакта

Сохранить `/outputs/result.json` как UTF-8 JSON следующей формы:

```json
{
  "completion_status": "complete",
  "disagreements": [
    {
      "status": "deviation",
      "matrix_item": {
        "id": "2.1",
        "text": "Полный исходный текст пункта матрицы"
      },
      "contract_items": [
        {
          "id": "3.4",
          "locator": "п. 3.4",
          "text": "Полный исходный текст пункта договора"
        }
      ],
      "comment": "В договоре установлен срок 5 дней вместо 10 дней, предусмотренных матрицей."
    }
  ]
}
```

Соблюдать следующие ограничения:

- для `deviation` заполнить `matrix_item` и включить в `contract_items` один или несколько принятых аналогов;
- для `missing_in_contract` заполнить `matrix_item` и передать пустой массив `contract_items`;
- для `extra_in_contract` установить `matrix_item` в `null` и включить в `contract_items` ровно одну исходную договорную единицу;
- для связанного приложения или таблицы использовать в `id` исходный номер ссылающегося пункта договора; в `locator` указать якорный пункт и точное место связанного материала, а в `text` привести полный текст якорного пункта и точный относящийся фрагмент приложения или таблицы;
- для непривязанного приложения или таблицы без собственного ID установить `id` в `null`, указать точное описание расположения в `locator`, а в `text` передать только точные юридически значимые фрагменты, относящиеся к разногласию, без копирования остального материала;
- устанавливать `completion_status` в `complete` только после проверки полноты;
- при невозможности завершить анализ не создавать итоговый JSON.
