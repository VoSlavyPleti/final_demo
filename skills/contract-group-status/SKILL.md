# Статусы групп с локальным восстановлением mapping

## Назначение

Прочитать `/AGENTS.md`, `/inputs/contract.txt`, `/inputs/matrix.json` и принятую
карту `/outputs/working/mapping.json`. Определить профиль договора, применимость
матрицы и статусы contract-oriented групп. Сохранить чистый JSON в
`/outputs/working/status.json`. Сначала зафиксировать предварительную оценку в
`/outputs/working/status-provisional.json`, затем отдельный журнал принятых
исправлений mapping в `/outputs/working/mapping-adjustments.json`.

Не выполнять полный mapping заново. Считать исходные группы baseline-гипотезами.
Исправлять состав `candidates` только локально, когда пустая, слабая или неполная
группа способна привести к ошибочному `extra_in_contract`, `missing_in_contract`
или `deviation`. Не изменять исходные `contract_id`, `contract_locator`, порядок и
число групп. Не формировать итоговый протокол разногласий.

До решений прочитать
`/skills/contract-group-status/references/calibration.md`. Применять примеры как
обязательную границу статусов и восстановления связи, но устанавливать факты
только по текущим источникам.

## 1. Профиль и применимость

Установить алиасы `Банка` и `Предприятия` по предмету, правам и обязанностям, а не
по словам `Заказчик` и `Исполнитель`. Установить закупочный режим, продукты,
способы оплаты и типы терминалов по выбранной опции, предмету, тарифу,
спецификации либо оперативному праву или обязанности.

Не выводить применимость из определения, общего перечня возможностей, пустого
поля, неотмеченного чекбокса или одной технической возможности. В частности,
способность дисплея показать QR-код не доказывает использование QR.

Непустые `only_for_lot`, `only_for_product`, `payment_method` и
`only_for_terminal` читать как OR внутри одного поля и AND между полями. Пустой
селектор не ограничивает применимость. Присваивать `not_applicable` только при
доказанном несовпадении непустого селектора. При недостатке данных считать
требование применимым. Строку без `required_type` считать структурной.

## 2. Предварительная оценка

Оценить baseline-группы по правилам раздела 4 и сохранить
`/outputs/working/status-provisional.json`:

```json
{
  "completion_status": "complete",
  "groups": [
    {
      "contract_id": "1.1",
      "evaluated_matrix_ids": ["2.1"],
      "status": "aligned|deviation|extra_in_contract|not_applicable",
      "comment": "",
      "difference_basis": null
    }
  ],
  "recovery_queue": [
    {
      "contract_id": "1.1|null",
      "matrix_id": "2.1|null",
      "reason": "empty_group|weak_candidate|uncovered_related_element|applicable_mandatory_unmapped"
    }
  ]
}
```

Включить в `recovery_queue` только конкретные случаи, способные изменить
предварительный статус: потенциальный `extra_in_contract`, слабого кандидата,
названную непокрытую часть того же механизма либо применимый mandatory-ID без
кандидата. Не пересматривать остальные группы после recovery.

Перед сохранением provisional оспорить каждый предполагаемый `aligned`, если
относящийся текст матрицы или договора содержит конкретный срок, дату, сумму,
ставку, формулу, роль, направление обязанности либо запускающее событие.
Сопоставить эти элементы внутри одного механизма. Любое подтверждённое различие
перевести в `deviation` с полным `difference_basis`; отсутствие различия оставить
`aligned`. Не искать при этой проверке новых кандидатов.

## 3. Локальное восстановление кандидатов

Обрабатывать только элементы `recovery_queue`. Для включённой baseline-группы
проверить, подтверждают ли её кандидаты общее оперативное правоотношение
доказательствами обоих источников. Совпадение только темы, слова, срока или суммы
связью не является.

Выполнить дополнительный поиск только в следующих случаях:

- `candidates` пуст, а пункт договора создаёт самостоятельное право, обязанность,
  ограничение или ответственность;
- доказательства кандидата относятся лишь к общей теме, противоречат выбранному
  `matrix_id` или описывают другой механизм;
- применимый обязательный пункт матрицы остался без кандидата;
- предполагаемое неполное покрытие может находиться в другом пункте договора.

Не запускать recovery только из-за отличия срока, даты, суммы, ставки, роли,
триггера или иного элемента при уже подтверждённом сильном кандидате. Это отличие
является status-задачей. Искать дополнительного кандидата лишь когда конкретная
непокрытая часть того же механизма может быть закреплена другим пунктом договора.

Искать только среди положений, относящихся к тому же обязательству или правовому
механизму. Проверить прямой аналог, затем корреспондирующее право и обязанность,
другой способ исполнения того же обязательства, функциональный юридический
синоним и инвертированное встречное действие. Наличие `matrix_id` в другой группе
не запрещает повторное использование.

Добавить кандидата при наличии общего оперативного механизма с тем же объектом и
правовой функцией. Различие роли, направления, триггера, срока, суммы, формы,
способа или объёма после установления механизма не уничтожает mapping и
оценивается статусом.

Особенно проверять:

- право потребовать оплату и обязанность оплатить те же услуги;
- односторонний отказ и одностороннее прекращение того же договора;
- приёмку услуг и подписание, возврат либо мотивированный отказ от документа
  приёмки;
- разные безналичные способы исполнения обязанности оплаты тех же услуг;
- зеркальные действия сторон в одном механизме.

Не сопоставлять фиксированный штраф за неисполнение, исключающий просрочку, с
пеней за просрочку; общую ссылку на закон — с любой специальной банковской
защитой; одинаковый срок — с посторонним обязательством. Не добавлять кандидата
ради уменьшения списка непокрытых ID.

Удалить baseline-кандидата только если оба доказательства не подтверждают
названное общее правоотношение. Для добавленного или сохранённого кандидата
зафиксировать точный `matrix_id`, `relation_type`, конкретный
`shared_legal_relation` и по одному непрерывному дословному фрагменту обоих
источников.

Перед добавлением найти объект матрицы по точному равенству поля `number`, заново
прочитать его `text` и сверить цитату. Не определять содержание строки по позиции
в массиве, соседнему номеру или памяти. Кандидат с пустым `contract_evidence` или
`matrix_evidence` недопустим.

После обработки recovery-очереди сохранить
`/outputs/working/mapping-adjustments.json`:

```json
{
  "completion_status": "complete",
  "changes": [
    {
      "contract_id": "4.4",
      "contract_locator": "Основной текст, п. 4.4",
      "action": "add|remove",
      "matrix_id": "4.2.12",
      "reason": "Краткое основание, подтверждённое обоими текстами"
    }
  ]
}
```

Зафиксировать каждое добавление и удаление ровно один раз. Пустой `changes`
допустим только после проверки всех перечисленных выше триггеров recovery.
Итоговые `candidates` в status-артефакте должны точно отражать этот журнал.
Итоговый набор кандидатов каждой группы должен быть равен baseline-набору плюс
зарегистрированные `add` минус зарегистрированные `remove`. Не удалять кандидата
только из-за неприменимости: сохранить его в `candidates`, исключив из
`evaluated_matrix_ids` и статусного основания.

Если основанием предварительного `deviation` является непокрытый элемент матрицы,
перед классификацией найти этот элемент во всём договоре. При обнаружении добавить
кандидата в группу того пункта договора, который действительно его содержит, а
не механически в текущую группу. Добавленную целевую группу считать затронутой
recovery и повторно оценить. Только после безуспешного поиска считать элемент
непокрытым.

## 4. Статус contract-oriented группы

Оценить всё юридически значимое содержание одного исходного пункта договора
относительно совокупности применимых итоговых кандидатов. Для каждого кандидата
сравнивать только общий сопоставленный механизм и непосредственно квалифицирующие
его условия. Самостоятельное содержание матричного пункта вне этого механизма
учитывается в его собственной matrix-oriented проверке, но не ухудшает статус
данной contract-oriented группы:

- `aligned` — весь относящийся смысл пункта договора имеет аналоги, а общий
  механизм и непосредственно квалифицирующие его элементы не изменены;
- `deviation` — юридический аналог есть, но относящаяся роль, обязанность,
  действие, объект, адресат, основание, триггер, способ, объём, срок, сумма,
  ставка или иной правовой эффект отсутствует, добавлен, изменён, ограничен либо
  инвертирован;
- `extra_in_contract` — после локального поиска у пункта нет ни одного
  юридического аналога;
- `not_applicable` — кандидаты существуют, но все они доказанно неприменимы.

Соблюдать инварианты статуса: `extra_in_contract` допустим только при пустом
итоговом `candidates`; `aligned` и `deviation` требуют хотя бы одного применимого
ID в `evaluated_matrix_ids`; при непустых `candidates` и отсутствии применимых ID
использовать `not_applicable`.

Не назначать `extra_in_contract`, если сохранился хотя бы один юридический аналог:
дополнительное относящееся условие такой группы оценивается как `deviation`.

Конкретные срок, дата, период, сумма, ставка, формула, база расчёта, единица и
событие начала отсчёта являются точными эталонами одного правоотношения. Любое их
отличие, включая более выгодное Банку, является `deviation`. Пустой шаблонный
параметр матрицы эталоном не является. Выбор одной из прямо разрешённых
альтернатив матрицы сохраняет `aligned`.

Пустое поле, линия для заполнения или placeholder договора не образуют
юридического условия. Не ставить `deviation` только потому, что соответствующее
поле матрицы заполнено: оценивать оперативную обязанность, к которой относится
значение. Не считать выбранную одну из альтернатив матрицы неполным покрытием.

Ссылка на 44-ФЗ или 152-ФЗ покрывает относящееся обязательное законодательное
содержание, если договор не содержит противоречия. Она не заменяет специальный
банковский срок, сумму, ставку, роль, способ или защиту.

Штрафные формулы, непосредственно рассчитанные от НМЦК по закупочному режиму, не
считать отклонением при пустом шаблонном значении матрицы. Антикоррупционные
оговорки не считать расхождением. Положения о ПДн считать согласованными при
применимой ссылке на 152-ФЗ, если договор не устанавливает противоречающего
правила или отдельного банковского условия.

Перед каждым `deviation` перечитать полный пункт договора и относящиеся фрагменты
всех кандидатов. В комментарии фиксировать только подтверждённое отличие в форме
`Матрица: …; договор: …`. Не требовать от одного пункта договора покрытия
самостоятельного содержания кандидата, относящегося к другому правоотношению.
Кандидат со статусом применимости `not_applicable` не включать в
`evaluated_matrix_ids` и не использовать как основание статуса или комментария.

Для каждого `deviation` заполнить `difference_basis`: точный тип отличия,
`matrix_id`, непустую дословную цитату матрицы, непустую относящуюся цитату
договора и краткое объяснение. Не присваивать `deviation`, если невозможно
заполнить все эти поля по текущим источникам. Отсутствие в одном пункте договора
самостоятельного содержания матричного кандидата вне сопоставленного механизма не
является отклонением этой contract-oriented группы.

После recovery пересчитать статус только групп из `recovery_queue`. Для остальных
групп дословно перенести статус, комментарий, `evaluated_matrix_ids` и
`difference_basis` из provisional-артефакта.

Для `extra_in_contract` установить `independent_legal_obligation: true` только
для самостоятельного права, обязанности, ограничения или ответственности.
Заголовок, определение, реквизит, поле формы и технический или справочный текст
такого эффекта не создают.

## 5. Статус строк матрицы

Создать по одному объекту `matrix_review` для каждого исходного `number`:

- `structural` — отсутствует `required_type`;
- `not_applicable` — доказанно не выполнен селектор;
- `mapped` — применимый ID присутствует хотя бы в одной итоговой группе;
- `missing_in_contract` — применимый mandatory-ID не присутствует ни в одной
  итоговой группе после локального поиска;
- `optional_absent` — применимый optional-ID остался без кандидата.

Optional-пункт при наличии аналога анализировать на общих основаниях. Его
отсутствие не является `missing_in_contract`.

## Формат артефакта

Сохранить `/outputs/working/status.json` как чистый валидный JSON:

```json
{
  "schema_version": "status.v2",
  "completion_status": "complete",
  "mapping_changes": [
    {
      "contract_id": "4.4",
      "contract_locator": "Основной текст, п. 4.4",
      "action": "add",
      "matrix_id": "4.2.12",
      "reason": "Краткое подтверждённое основание"
    }
  ],
  "contract_profile": {
    "bank_aliases": ["Исполнитель"],
    "counterparty_aliases": ["Заказчик"],
    "lot_regimes": ["fz_44"],
    "products": ["trade_acquiring"],
    "payment_methods": [],
    "terminal_types": [],
    "evidence": [{"locator": "п. 1.1", "quote": "Дословный фрагмент"}]
  },
  "groups": [
    {
      "contract_id": "1.1",
      "contract_locator": "Основной текст, п. 1.1",
      "candidates": [
        {
          "matrix_id": "2.1",
          "relation_type": "direct",
          "shared_legal_relation": "конкретный общий механизм",
          "contract_evidence": "дословный фрагмент",
          "matrix_evidence": "дословный фрагмент"
        }
      ],
      "evaluated_matrix_ids": ["2.1"],
      "status": "aligned|deviation|extra_in_contract|not_applicable",
      "comment": "",
      "difference_basis": {
        "difference_type": "term|date|amount|rate|role|trigger|method|scope|legal_effect|other",
        "matrix_id": "2.1",
        "matrix_quote": "дословный фрагмент",
        "contract_quote": "дословный фрагмент",
        "explanation": "Краткое конкретное отличие"
      },
      "source_kind": "main_body|appendix|glossary|heading|requisites|technical_or_reference|null",
      "independent_legal_obligation": true
    }
  ],
  "matrix_review": [
    {
      "matrix_id": "2.1",
      "required_type": "mandatory|optional|null",
      "applicability": "applicable|not_applicable|structural",
      "coverage_status": "mapped|missing_in_contract|optional_absent|not_applicable|structural",
      "reason": "Краткое фактическое основание"
    }
  ]
}
```

Для не-extra групп устанавливать `source_kind` и
`independent_legal_obligation` в `null`. Для `aligned` оставлять `comment` пустым.
Для всех статусов, кроме `deviation`, устанавливать `difference_basis` в `null`.
Поле `mapping_changes` дословно копирует массив `changes` из принятого
`mapping-adjustments.json`.

## Самопроверка

Перед `completion_status: "complete"` проверить:

- число, порядок, `contract_id` и `contract_locator` групп совпадают с baseline;
- все итоговые candidate-ID существуют в матрице, не повторяются внутри группы и
  имеют проверяемые дословные доказательства;
- `mapping_changes` точно объясняет разницу между baseline и итоговыми
  `candidates`, без незафиксированных добавлений или удалений;
- для каждой группы итоговый набор кандидатов механически воспроизводится из
  baseline и `mapping_changes`;
- provisional содержит все baseline-группы; финальная оценка незатронутых групп
  дословно совпадает с provisional;
- каждый добавленный кандидат имеет непустые дословные доказательства обоих
  источников и содержание найдено по точному `number`;
- каждый `deviation` имеет полный `difference_basis` и согласованный комментарий;
- нет `extra_in_contract` с кандидатами и нет `aligned` или `deviation` без
  применимых `evaluated_matrix_ids`;
- каждому `number` соответствует ровно один `matrix_review`;
- каждый применимый mandatory-ID после recovery является mapped или
  `missing_in_contract`;
- каждый статус и комментарий согласуются с полными исходными текстами.

После проверки повторно прочитать сохранённый JSON и вернуть оркестратору только
путь к файлу.
