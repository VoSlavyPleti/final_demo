# Спецификация проекта Contract Matrix Review

Состояние реализации: **31 августа 2026**, ветка **`ws-first`**.
Документ описывает фактический код, а не план будущих возможностей.
Параметры запуска приведены в разделе 8, диагностика — в разделе 15.

## 1. Назначение документа

Этот документ описывает текущее назначение, бизнес-логику, архитектуру,
технологический стек и процесс улучшения качества проекта. Спецификация
фиксирует границу между агентным юридическим анализом и инфраструктурным
кодом harness-системы.

Источники истины: параметры и lifecycle — код; юридическая методика —
domain skill и его references; схема — `references/output-schema.md`.
SPEC не загружается анализирующему агенту и не является дополнительным prompt.

## 2. Что это за проект

Contract Matrix Review — автономный ИИ-ассистент для первичного анализа
договоров эквайринга в банке. Он сопоставляет полный текст проекта договора с
банковской матрицей типовых требований и формирует проверяемую карту
соответствий и расхождений.

Основной пользователь системы — банковский юрист. Система не заменяет его
решение: её задача — прочитать большой договор целиком, не пропустить
операционные положения, связать их с релевантными требованиями матрицы и
сократить объём ручного поиска.

Технический результат анализа — полная many-to-many карта в JSON. Она
содержит как совпавшие положения, так и расхождения. Пользовательский слой,
если он будет добавлен отдельно, может показывать юристу только расхождения,
но полнота внутренней карты необходима для контроля покрытия и расчёта метрик.

## 3. Бизнес-цель

Система должна находить три класса значимых расхождений:

1. `deviation`: в договоре найден полный или частичный смысловой аналог строки
   матрицы и целевая дельта casebook — например, изменение суммы, срока,
   триггера, объёма обязанности, права, запрета, способа исполнения, последствия
   или распределения риска.
2. `extra_in_contract`: пункт договора создаёт самостоятельную дополнительную
   обязанность стороны, для которой во всей матрице нет смыслового аналога.
3. `missing_in_contract`: обязательная и применимая строка матрицы не имеет во
   всём договоре и относящихся приложениях ни полного, ни частичного
   смыслового аналога.

Система также использует служебные статусы:

- `aligned` — смысловой аналог найден, целевой дельты casebook нет;
- `not_applicable` — неактивный вариант операционного условия;
- `needs_review` — в доступных источниках отсутствует конкретный факт, без
  которого статус нельзя определить надёжно.

## 4. Основная модель юридического анализа

### 4.1. Единица анализа

Каждый исходный пункт договора оценивается отдельно. Контекстом пункта могут
быть его ненумерованное продолжение, определения, явные ссылки и относящиеся
положения приложений. Разные исходные номера не объединяются в искусственные
пункты.

Номер пункта является только идентификатором. Совпадение нумерации, названия
раздела или положения в структуре документов не является доказательством
смыслового соответствия.

### 4.2. Смысловое many-to-many сопоставление

Смысловой аналог существует, если договор и матрица регулируют одно
правоотношение и имеют хотя бы одно общее действующее положение: право,
обязанность, запрет, условие, триггер, последствие или механизм с тем же
юридическим результатом.

Одному пункту договора могут соответствовать несколько строк матрицы, а одна
строка матрицы может покрываться несколькими пунктами договора. Покрытие
требования матрицы оценивается по совокупности найденных аналогов.

Общая тема, сторона, термин, одинаковое число или одинаковый срок для разных
событий сами по себе смыслового аналога не создают.

### 4.3. Граница `deviation` и `missing_in_contract`

Если найден хотя бы частичный смысловой аналог, строка матрицы не может
одновременно считаться отсутствующей. Агент должен искать дополнительные
аналоги, способные покрыть оставшуюся часть того же правоотношения. Если
совокупное покрытие всё равно неполно и непокрытая часть является целевой дельтой casebook, статус
соответствующего пункта договора — `deviation` с описанием непокрытой части, а
не сочетание `deviation` и `missing_in_contract`.

`missing_in_contract` допустим только при одновременном выполнении трёх
условий: строка имеет `required_type = mandatory`, все её селекторы
положительно подтверждены договором, и смысловой аналог отсутствует во всех
доступных частях договора.

### 4.4. Индивидуальность статусов

Каждый пункт получает статус по собственному юридическому эффекту.
Совпадающее положение в другом месте договора не устраняет прямое
противоречие отдельного пункта. Если пункт ссылается на противоречащее
приложение или другой пункт, расхождение описывается со ссылкой на оба
источника.

Для смешанного пункта применяется единый порядок policy: отсутствует необходимый
внешний текст — `needs_review`; неактивный вариант — `not_applicable`; нет
аналога — `extra_in_contract`; есть аналог и целевая дельта — `deviation`;
иначе — `aligned`. Наличие нескольких аналогов не создаёт несколько статусов.

Единица идентичности — исходное вхождение, а не номер сам по себе.
Повторяющиеся номера не объединяются: они различаются через `source_locator`.

### 4.5. Применимость матрицы

Поля `only_for_product`, `only_for_lot`, `payment_method` и
`only_for_terminal` являются селекторами применимости. Их значение считается
активированным только при положительном подтверждении в операционном тексте
договора или заполненном приложении.

Селекторы ограничивают только matrix-side поиск missing, но не отменяют
доказанный сильный contract-side аналог. Активность продуктовой группы не
доказывает отдельное локальное условие применимости конкретной строки.

Определение термина, пустая типовая форма, перечисление потенциальных
вариантов, незаполненный checkbox или единичное слабое тематическое совпадение
не подтверждают применимость. Область договора определяется по прямым
операционным положениям либо по согласованной группе сильных смысловых
аналогов.

### 4.6. Неоперационные положения

Заголовки, оглавление, реквизиты, подписи, определения без собственной нормы,
технические поля и специальные положения закона без дополнительной
операционной обязанности не являются `extra_in_contract`. Они учитываются
агентом в рабочем перечне, но не публикуются в `contract_items`. Подписываемое
заверение, согласие, акцепт или подтверждение в форме/акте может само быть
операционным положением и не исключается только по расположению в приложении.

### 4.7. Placeholders и `main_idea`

По C01 placeholder в действующем сопоставленном условии договора всегда
является `deviation`, если соответствующее значение матрицы заполнено.
Это относится и к датам, суммам, URL, e-mail, адресам и идентификаторам
исполнения, в том числе в приложенной форме. Открытое поле самой матрицы,
его заполнение договором и неоперационные реквизиты сторон не образуют C01.

Поле матрицы `main_idea` используется только как поисковая подсказка. Оно не
является нормативным текстом, не создаёт требования и не может самостоятельно
обосновать статус.

## 5. Входы и выходы

### 5.1. Входные данные

- договор в UTF-8 TXT;
- банковская матрица в JSON;
- domain skill `contract-matrix-review` со всеми обязательными reference-файлами.

OCR и извлечение текста из сканов не входят в текущий сценарий. Приложения,
которые должны участвовать в анализе, должны присутствовать в переданном TXT.

Матрица — непустой JSON-массив объектов. В текущем файле используются поля
`number`, `text`, `required_type`, `only_for_product`, `only_for_lot`,
`payment_method`, `only_for_terminal`, `main_idea`. Номер строки берётся из
`number`, нормативное требование — из `text`. Harness не переписывает эти поля
и проверяет контейнер JSON, но не полноту бизнес-схемы каждой строки.
Нумерация и вхождения приложений должны быть сохранены при подготовке TXT;
номер с завершающей точкой и номер перед пробелом одинаково учитываются.
XLSX gold, `.env`, сертификаты и SPEC не монтируются агенту.

### 5.2. Итоговый артефакт

Единственный пользовательский артефакт запуска — UTF-8 JSON по схеме
`contract-matrix-map.v6`:

```json
{
  "schema_version": "contract-matrix-map.v6",
  "contract_items": [
    {
      "contract_id": "5.2",
      "source_locator": "основной текст, раздел 5",
      "matrix_ids": ["3.1", "3.4"],
      "status": "deviation",
      "comment": "Срок возврата увеличен с 5 до 10 рабочих дней."
    }
  ],
  "matrix_items": [
    {
      "matrix_id": "7.3",
      "status": "missing_in_contract",
      "comment": "Mandatory-требование применимо, но его аналог отсутствует во всём договоре."
    }
  ]
}
```

`contract_items` содержит результаты относительно пунктов договора.
`matrix_items` используется только для `missing_in_contract` и
`needs_review`, относящихся к строкам матрицы.

`source_locator` обязателен для каждого повторяющегося номера, пункта
приложения и ненумерованного операционного положения; для однозначного пункта
основного текста он опционален. Номера нельзя синтезировать или исправлять.
В результате нет поля `completion_status`: готовность определяется завершением
запуска и структурным gate, а не дополнительным маркером в схеме.

Полные тексты документов, внутренние рассуждения модели, калибровочные метки и
служебные audit-поля в итоговый JSON не включаются.

## 6. Архитектура

| Слой | Ответственность | Основные файлы |
|---|---|---|
| CLI и supervisor | Валидация, staging, разделение model retry и полного restart, атомарная публикация | `main.py` |
| AEF WorkStation | HTTPS-клиент, lifecycle одноразовой сессии и реализация `SandboxBackendProtocol` | `aef_workstation.py` |
| Модель | Корпоративный GigaChat adapter с `glm-5.2`, сертификаты, лимиты, timeout/close | `llm.py` |
| Консоль | Содержательные события модели и инструментов отдельно от безопасного trace | `console_logging.py` |
| Оркестрационные prompts | Роль, границы, виртуальные пути и формулировка запуска | `prompts/` |
| Domain skill | Вся юридическая методология сопоставления, статусов, применимости и комментариев | `skills/contract-matrix-review/` |
| Runtime paths | Привязка виртуальных путей к `/workspace` внутри WorkStation; локальный Windows backend — только явный rollback | `harness_runtime/sitecustomize.py`, `aef_workstation.py`, `main.py` |
| Quality gate | Только структура, схема и внутренние инварианты JSON; без юридической классификации | `quality_gate_failures()` в `main.py` |
| Benchmarking | Проверенные gold-наборы и расчёт mapping/status/classification-метрик | `benchmarks/`, `gold_results/` |
| Тесты | Контракты harness, prompts, skill, paths, retry и publication flow | `tests/` |

### 6.1. Агентный runtime

На каждую инфраструктурную попытку harness создаёт новый Deep Agent через
`create_deep_agent()`. Он получает модель, новый `MemorySaver`, новый thread,
один экземпляр AEF backend и domain skill из родительского каталога
`/skills/`. Тот же backend автоматически разделяют главный агент и стандартные
`general-purpose` subagents. Собственные доменные инструменты или схема
специализированных сабагентов не задаются: агент использует стандартные
возможности Deep Agents и сам выбирает способ выполнения задачи.

Юридический matching, оценка применимости и присвоение статусов выполняются
агентом. Python-код не должен содержать регулярные выражения, таблицы решений
или детерминированные эвристики, подменяющие юридическое суждение.
Архитектура является LLM-only на всём семантическом контуре: проект и harness
не предоставляют заранее реализованные embeddings, векторные индексы,
retrieval/reranking, доменные классификаторы или инструменты поиска кандидатов.
Стандартные файловые и shell-возможности остаются доступными агенту. Агент
может в ходе конкретного запуска сам создавать временные скрипты для выбранного
им способа анализа, проверки или сериализации; такие скрипты являются частью
его работы в текущем workspace и не превращаются в постоянный инструмент
harness.

### 6.2. Изолированный workspace

На каждый запуск локально создаётся контрольный staging-каталог
`contract-review-*`. В каждую AEF-попытку его неизменяемые файлы загружаются в
новую одноразовую сессию со следующей виртуальной структурой:

```text
inputs/contract.txt
inputs/matrix.json
skills/contract-matrix-review/
.harness_runtime/sitecustomize.py
outputs/working/
outputs/result.json
tmp/
```

`AefWorkstationBackend` преобразует любой виртуальный путь `/<path>` в
`/workspace/<path>` и не раскрывает физический `workspaceRoot` сервиса. Прямые
`write`, `edit` и `upload` запрещены для `/inputs`, `/skills` и
`/.harness_runtime`; после каждого `execute` повторно сверяются полный набор
путей и типов узлов этих каталогов, а для файлов — также SHA-256. Обход дерева
не имеет серверного ограничения глубины.
Agent-authored Python получает ограниченное отображение известных виртуальных
корней через `sitecustomize.py`. Shell в AEF является POSIX и начинает работу в
`/workspace`.

После gate result, trace и manifest публикуются соседними файлами через
`os.replace`; manifest публикуется последним. Успешный локальный staging
удаляется по умолчанию и сохраняется с флагом `--keep-workspace`. При ошибке он
сохраняется для диагностики, а failed trace и manifest атомарно публикуются
рядом с целевым output без публикации `result.json`. Удалённая сессия
завершается независимо от этого флага. S3 persistence и автоматический
fallback на локальную файловую систему не используются.

### 6.3. Повторы и quality gate

Повторы модели выполняются в том же thread только пока WorkStation остаётся
здоровой. Для AEF скрытые SDK-retries отключены: повтором управляет harness
после проверки session health. Перед каждым model call его transport timeout
ограничивается остатком безопасного TTL; во время streaming deadline
проверяется на каждом chunk. Отдельный wall-clock watchdog наблюдает за deadline
и закрывает выделенный model HTTP client при его наступлении. Это best-effort
прерывание клиента, а не отмена серверного вычисления или гарантия остановки
потока ОС ровно в заданную миллисекунду; последующая health-проверка запрещает
публикацию просроченного результата. При полном restart создаётся новый model client. Безопасные
операции чтения могут повторяться с full-jitter backoff.
Неоднозначный результат произвольного `execute` никогда не повторяется в той же
сессии: попытка помечается недостоверной, уничтожаются session/backend/agent/
checkpointer/thread, и весь анализ один раз запускается заново в чистой
сессии. Невалидный итоговый JSON не получает скрытого repair-прохода и не
публикуется.

Quality gate проверяет:

- наличие и читаемость UTF-8 JSON;
- версию схемы и точный набор полей;
- допустимые статусы;
- уникальность `matrix_id` и различимость повторяющихся `contract_id` через
  непустые уникальные `source_locator`;
- обязательность `matrix_ids` для `aligned` и `deviation`;
- отсутствие одновременного mapping и `missing_in_contract` для одной строки
  матрицы.

Gate намеренно не проверяет юридическую полноту, правильность соответствий и
статусов. Такая механическая проверка создала бы скрытую вторую методологию и
нарушила бы агентную архитектуру.

Gate не сверяет существование каждого ID с исходным текстом и не может
доказать полноту списка операционных пунктов. Он проверяет строковое
различие locators, но не тождество описанных ими исходных мест. Полнота,
корректность локализации и обязательность locator для приложения — задачи
агентной самопроверки и последующей экспертной оценки.

### 6.4. Наблюдаемость

`CompactTraceHandler` и AEF-клиент сохраняют только allow-listed метаданные
model/tool/HTTP/lifecycle событий. В этот audit trace не записываются документы,
prompts, команды, stdout/stderr, token, create secret, multipart body и
физический `workspaceRoot`. Рядом с результатом публикуются `<name>.trace.jsonl` и
`<name>.manifest.json`; manifest содержит SHA-256 входов, skill, runtime и
результата, а также безопасную историю попыток и cleanup.
Manifest содержит полный отсортированный перечень реально смонтированных
staging-файлов с размерами и SHA-256. Этот snapshot снимается один раз до
создания сессии и не пересчитывается из изменяемых исходных путей после запуска.

Отдельный `ConsoleLogHandler` в режиме `AGENT_CONSOLE_LOG=full` (по умолчанию)
выводит в stdout полное содержимое входных сообщений и промежуточных/финальных
ответов модели, имена и аргументы инструментов, их результаты, включая
stdout/stderr `execute`. Он наследуется вызовами general-purpose. Записи имеют
время и run/parent IDs, выводятся с flush и без дополнительного усечения;
ограничения самих инструментов остаются в силе. При текущем `streaming=False`
ответ печатается после каждого завершённого модельного вызова. Если провайдер
возвращает `reasoning_content`, оно тоже отображается; недоступные внутренние
рассуждения не восстанавливаются.

Полный console log намеренно содержит конфиденциальные договорные данные,
поэтому stdout среды выполнения должен быть защищён. Известные секреты из
окружения, Bearer/Basic credentials и PEM private keys маскируются; сырые
конфигурации клиента и HTTP body/headers ошибок GigaChat не печатаются.
Это не универсальный DLP-фильтр. `AGENT_CONSOLE_LOG=compact` либо
`--console-log compact` отключает содержательный вывод, оставляя технические
события. В `.trace.jsonl` подробный консольный вывод не дублируется.

## 7. Backend API и технологии

### Реализация файловых инструментов WorkStation

Backend напрямую реализует `SandboxBackendProtocol`, без `BaseSandbox` и
без подмены удалённого execute локальными командами.

| Операция | Реализация / семантика |
|---|---|
| `id` | ID текущей одноразовой сессии |
| `ls` | `files:list`, только непосредственные потомки |
| `read` | `files:download`, размер/SHA, UTF-8, line offset/limit |
| `write` | Create-only: проверка отсутствия, mkdir родителя, upload, SHA |
| `edit` | Download, точная строковая замена с проверкой совпадений, upload/SHA |
| `glob` | Обход дерева сервиса, локальное применение glob-шаблона |
| `grep` | Буквальный текстовый поиск; не embeddings и не regex matching юридических норм |
| `upload_files` | Последовательная загрузка, защищённые корни закрыты агенту |
| `download_files` | До четырёх параллельных скачиваний |
| `execute` | Синхронный `POST /v1/sessions/{session_id}/exec` |

Preflight вызывает `GET /health/readiness`, `GET /version`,
`GET /openapi.json`; lifecycle использует `POST /v1/sessions`,
`GET /v1/sessions/{session_id}`, `POST /v1/sessions/{session_id}:terminate`.
Файловые операции — POST endpoints `files:list`, `files:upload`,
`files:download` под текущей сессией. Внешний сервис не модифицировался.

Преобразование `/<path>` → `/workspace/<path>` универсально и включает
`/large_tool_results`, `/conversation_history` и будущие служебные каталоги.
Проверяются traversal, NUL, Windows drive paths и выход за `/workspace`.
Кеш файла привязан к пути/SHA; после execute инвалидируется весь кеш.
Один writer-preferring readers-writer lock разделяется всеми агентами сессии:
чтения параллельны, изменения и execute эксклюзивны, heartbeat не ждёт этот lock.

Execute передаёт `command=["sh", "-lc", wrapper]`, `cwd=/workspace`,
`LANG/LC_ALL=C.UTF-8`, `stdin=null`, `stdinEncoding=utf8`. Wrapper задаёт
`PYTHONPATH`, `DEEPAGENT_WORKSPACE_ROOT`, `PYTHONUTF8`, `PYTHONIOENCODING`.
`sitecustomize.py` отображает известные виртуальные корни для agent-authored
Python; для shell рекомендуются относительные пути. Это вспомогательный path
adapter, не универсальная файловая виртуализация всех программ в контейнере.

`timeout=None` или 0 означает фактическую execute-квоту сессии, а не бесконечное
выполнение. Значение выше квоты возвращает tool error. HTTP read timeout равен
command timeout + 30 секунд. `timedOut=true` и HTTP 504 в текущем клиенте
отображаются в exit code 124. Серверное усечение сохраняется; дополнительно
вывод execute ограничен 400 000 символов. Защита исходников от execute — это
проверка неизменности после команды с потерей попытки при изменении, а не
read-only mount на уровне ОС.

### Политика повторов и восстановления

| Операция | Фактическая политика |
|---|---|
| Safe status/list/download/preflight | До 4 попыток на transport и 408/429/500/502/503/504 |
| Create с потерянным ответом | Новый случайный ID; прежний отмечается orphan |
| Upload с неоднозначным ответом | Reconcile по SHA: совпало — успех, отсутствует — повтор, иной SHA — потеря попытки |
| Внутренний mkdir | Контролируемый повтор после проверки каталога |
| Произвольный execute | Не повторяется после transport/неоднозначного 5xx; полный restart |
| Execute 409 | Status-check и один повтор только при ready |
| Execute 400/403/413/422/429 | Tool error; дальнейшие действия выбирает агент |
| Execute timeout / HTTP 504 | Exit 124 без автоматического повтора команды |
| Model API | До 3 повторов invoke по умолчанию в том же thread, при здоровой AEF-сессии |
| Terminate | 200/404 — успех, 409 — ограниченный poll/retry; cleanup budget 30 секунд |

AEF safe retries: full jitter 0,5–8 секунд с поддержкой `Retry-After`.
Model retry использует отдельный backoff `min(2**(attempt+1), 30)` секунд.
Это две разные политики, не один общий механизм. Ошибки конфигурации,
протокола и gate не запускают слепые полные повторы. `AefAttemptLost` —
отдельный `RuntimeError`, который не поглощается model retry.

Exactly-once для произвольной shell-команды не обеспечивается. После
неоднозначного execute текущая сессия/graph/checkpointer/thread отбрасываются;
следующая попытка, если разрешена, начинает анализ с чистых входов. Командные
внешние эффекты первой попытки нельзя автоматически откатить: не выдавать
контейнеру лишние сетевые полномочия. Возобновления после перезапуска процесса
по сохранённому MemorySaver нет. Очистка best-effort: её неуспех фиксируется в
manifest и сам по себе не отменяет уже успешно проверенный результат.

## 8. Сценарий запуска

### 8.1. Установка

Нужна машина с доступом к корпоративному model gateway и WorkStation, DNS,
доверенными CA и клиентскими сертификатами. Модель вызывается с машины harness;
shell-команды агента выполняются отдельно в WorkStation. Переменная `LOCAL`
не переносит модель внутрь WorkStation.

Из каталога проекта, после переключения на `ws-first`:

```powershell
python -m pip install -r requirements.txt
```

Использовать интерпретатор подготовленного окружения проекта; тесты запускать
тем же `python`. В новой среде можно сначала создать venv и активировать его.
Не менять окружение/версии пакетов посередине долгого анализа.

Перед обновлением со старого checkout сохранить свой `.env` вне репозитория:
раньше он отслеживался Git, теперь исключён из текущего дерева. История старых
коммитов не очищена; если в них были действующие секреты, нужна их ротация.
Для нового checkout безопасно создать шаблон без перезаписи существующего файла:

```powershell
if (-not (Test-Path -LiteralPath .env)) {
    Copy-Item -LiteralPath .env.example -Destination .env
}
```

Заполнить реальные пути и host; значения `gateway.company.invalid` и пути
сертификатов в шаблоне иллюстративные. Не коммитить `.env`, private keys и логи
с договорными данными.

### 8.2. Конфигурация

Модель читает `.env` в корне проекта, приоритет имеет окружение процесса.
Имена переменных сохранены из корпоративного примера (см. `.env.example`):

```dotenv
LOCAL=true
GIGACHAT_HOST=<корпоративный host без схемы и порта>
GIGACHAT_PORT=443
GIGACHAT_ENDPOINT=/v1
GIGACHAT_TLS_CERT_FILEPATH=<путь к клиентскому сертификату>
GIGACHAT_KEY_FILEPATH=<путь к приватному ключу>
GIGACHAT_CA_BUNDLE_FILEPATH=<путь к корпоративному CA при необходимости>
```

`LOCAL=true` означает HTTPS с клиентскими сертификатами; `LOCAL=false`
(как в исходном примере — значение по умолчанию) означает HTTP через внутренний
gateway без загрузки клиентских сертификатов. Это выбор схемы подключения
модели, а не выбор filesystem backend. Автоматического переключения схемы нет.
Относительные пути сертификатов разрешаются от корня проекта. При отсутствии
host/port или обязательных файлов сертификатов запуск завершается ошибкой.

В отличие от предоставленного примера, TLS verification включена по умолчанию,
как рекомендует [официальный адаптер](https://github.com/ai-forever/langchain-gigachat/blob/master/libs/gigachat/README.md).
`GIGACHAT_VERIFY_SSL_CERTS=false` допускает явное отключение для диагностики;
для рабочего подключения нужно задавать CA, а не отключать проверку.
Эти настройки не меняют отдельную HTTPS-политику WorkStation.
Сертификаты и ключи остаются на машине harness и не загружаются агенту.

Встроенные SDK-retries отключены; transient HTTP `408/429/500/502/503/504`
и transport errors обрабатывает harness, с проверкой здоровья AEF перед
повтором. `401/403/404/413/422` не повторяются. В сообщении об ошибке API нет
сырых response body/headers. Таймаут GigaChat, кешированного SDK и HTTP-клиента
ограничивается дедлайном AEF; watchdog закрывает именно GigaChat-клиент.

Пример запуска:

Пути задаются в `.env` рядом с `main.py`:

```dotenv
AGENT_CONTRACT_PATH=inputs/contract.txt
AGENT_MATRIX_PATH=inputs/matrix.json
AGENT_OUTPUT_PATH=outputs/result.json
AGENT_CONSOLE_LOG=full
```

После заполнения этих параметров достаточно `python main.py`. Допустимы
абсолютные пути и относительные пути от корня проекта. CLI имеет приоритет;
его относительные пути, как и раньше, считаются от текущего каталога запуска.
Если обязательный путь не задан ни в CLI, ни в окружении, запуск завершается
до обращения к модели или WorkStation с указанием недостающей переменной.
Skill и runtime по-прежнему загружаются из штатных каталогов проекта.
Пути `.trace.jsonl` и `.manifest.json` выводятся из `AGENT_OUTPUT_PATH`.

Пример переопределения путей через CLI:

```powershell
python -u main.py `
  --contract kaluga.txt `
  --matrix inputs/matrix.json `
  --output demo_results/kaluga-result.json
```

Для всех путей из `.env`: `python -u main.py`. Ключ `-u` отключает буферизацию
Python stdout/stderr. В коде callback-события также печатаются с flush.
Прямые переменные окружения имеют приоритет над `.env`; CLI — над env-путями,
режимом логирования и backend. Значения `.env` загружаются при старте процесса;
изменение файла не перенастраивает уже работающий анализ.

| Переменная | Требование / default |
|---|---|
| `AGENT_CONTRACT_PATH` | Путь TXT, обязателен без `--contract` |
| `AGENT_MATRIX_PATH` | Путь JSON, обязателен без `--matrix` |
| `AGENT_OUTPUT_PATH` | Путь итогового `.json`, обязателен без `--output` |
| `AGENT_CONSOLE_LOG` | `full` по умолчанию; альтернатива `compact` |
| `AGENT_BACKEND` | `aef` по умолчанию; `local` только явный rollback |
| `LOCAL` | `false` по умолчанию; для HTTPS/mTLS установить `true` |
| `GIGACHAT_HOST` / `GIGACHAT_PORT` | Обязательны; hostname без схемы/порта, порт 1–65535 |
| `GIGACHAT_ENDPOINT` | `/v1` по умолчанию |
| `GIGACHAT_TLS_CERT_FILEPATH` / `GIGACHAT_KEY_FILEPATH` | Обязательные существующие файлы при `LOCAL=true` |
| `GIGACHAT_CA_BUNDLE_FILEPATH` | Опциональный CA для HTTPS; относительный путь от проекта |
| `GIGACHAT_VERIFY_SSL_CERTS` | `true`; не отключать в рабочем профиле |
| `AEF_WORKSTATION_BASE_URL` | Тестовый HTTPS origin, указанный ниже |
| `AEF_WORKSTATION_ENV` | `test`; метка окружения, сама по себе не меняет URL |
| `AEF_CA_BUNDLE` | Опциональный CA WorkStation; рекомендуется абсолютный путь (относительный — от cwd) |
| `AEF_SESSION_CREATE_SECRET` | Опционален, зависит от настройки стенда |
| `AEF_IDLE_TIMEOUT_SEC` | `900` |
| `AEF_ABSOLUTE_TTL_SEC` | `3600` |
| `AEF_HEARTBEAT_SEC` | `60` |

Session token WorkStation получается при create, вручную его задавать не нужно.
Сертификаты GigaChat и CA WorkStation — независимые настройки. В режиме
`LOCAL=false` пути клиентских сертификатов из примера не загружаются.
Остальные параметры `AefSettings` (число safe attempts, lock/download limits,
cleanup budget) заданы в Python и не имеют одноимённых env-переключателей.

По умолчанию используется профиль `aef` и тестовый URL
`https://workstation.dev0.apps.azwx5oj1.k8s.delta.sbrf.ru`. Token сессии
возвращает сервис; create secret и корпоративный CA задаются только через
`AEF_SESSION_CREATE_SECRET` и `AEF_CA_BUNDLE`. HTTPS verification включена,
redirects и downgrade на HTTP запрещены.

Конфигурация тестового профиля:

```text
AGENT_BACKEND=aef
AEF_WORKSTATION_BASE_URL=https://workstation.dev0.apps.azwx5oj1.k8s.delta.sbrf.ru
AEF_WORKSTATION_ENV=test
AEF_CA_BUNDLE=<корпоративный CA, если необходим>
AEF_SESSION_CREATE_SECRET=<из secret store, если проверка включена>
AEF_IDLE_TIMEOUT_SEC=900
AEF_ABSOLUTE_TTL_SEC=3600
AEF_HEARTBEAT_SEC=60
```

URL и значения TTL имеют показанные test-defaults. Секреты не хранятся в
репозитории и передаются только через environment/secret store. Фактический
`expiresAt`, возвращённый WorkStation, имеет приоритет над запрошенным TTL;
стенд, выдавший absolute TTL меньше запрошенного, считается несовместимым.
Безопасный deadline попытки наступает за десять минут до `expiresAt`: после
него новые model/tool операции блокируются, а результат уже выполнявшегося
вызова не может быть опубликован.

Дополнительные параметры:

- `--console-log full|compact` — переопределить режим консоли из `.env`;
- `--keep-workspace` — сохранить временный workspace после успешного запуска;
- `--max-retries N` — ограничить повторы model API в текущем здоровом thread;
- `--max-infra-restarts N` — ограничить полные AEF-restart; по умолчанию один;
- `--backend local` — явный rollback до начала запуска, без автоматического
  переключения при ошибке AEF.

`--max-retries` по умолчанию равен 3, принимает неотрицательное число повторов
после исходного invoke. `--max-infra-restarts` допускает только 0 или 1.
Один полный запуск CLI анализирует один TXT по одной матрице; пакетного CLI
нет. Для другого документа выполняется отдельная команда. Параллельные
запуски должны иметь разные `--output`: межпроцессной блокировки публикации нет.
Локальный rollback выполняет код на машине harness и не является защитной
песочницей, эквивалентной WorkStation.

Полный поток выполнения:

1. Harness до создания workspace проверяет UTF-8 и непустоту договора,
   непустой JSON-массив объектов матрицы, frontmatter и обязательные references
   skill, а также синтаксическую корректность `sitecustomize.py`.
2. Строится immutable staging manifest с размерами и SHA-256 договора,
   матрицы, skill и runtime; затем проверяются HTTPS readiness, version и
   обязательные операции `/openapi.json` тестового WorkStation.
3. Создаётся новая AEF-сессия без persistence, файлы загружаются и сверяются по
   SHA-256, запускается heartbeat.
4. Агент читает системный prompt, пользовательскую задачу, весь skill и его
   обязательные references.
5. Агент самостоятельно исследует документы, строит полную карту и записывает
   `outputs/result.json`.
6. Harness проверяет здоровье сессии и SHA исходников, скачивает результат и
   применяет механический gate.
7. Supervisor делает завершающую health/integrity проверку и в `finally`
   останавливает heartbeat и завершает сессию, фиксируя результат cleanup.
8. CLI повторно проверяет локально скачанный JSON и публикует result/trace,
   затем manifest. Атомарен каждый файл по отдельности, не вся тройка файлов.
9. Отдельной командой evaluator сравнивает результат с проверенным gold-набором;
   основной CLI автоматически метрики не рассчитывает.

После успешного запуска: `<name>.json`, `<name>.trace.jsonl`,
`<name>.manifest.json`; код возврата 0. Обработанная ошибка выполнения даёт 1,
ошибка аргументов — 2. Аварийное завершение процесса/прерывание может не успеть
опубликовать диагностику. Старый опубликованный результат при неудачном новом
запуске не удаляется: проверять нужно свежий manifest `status`, `run_id` и SHA,
а не только наличие JSON. Не использовать такой старый результат как новый.

## 9. Контур оценки качества

### 9.1. Gold-данные

Юридическая разметка хранится в `gold_results/*.xlsx`. Для машинной оценки она
аудируется и преобразуется в verified gold JSON в `benchmarks/`.

Перед использованием gold необходимо:

- исключить заголовки, глоссарий, реквизиты и иные неоперационные элементы;
- проверить, что `extra_in_contract` действительно содержит самостоятельную
  обязанность;
- восстановить пропущенные смысловые mapping-кандидаты;
- исключить из missing optional- и неподтверждённо применимые строки;
- не создавать новый gold deviation только из-за восстановленного mapping,
  если юристы не считали это расхождением;
- фиксировать источники и SHA-256, чтобы исключить незаметную смену версии
  договора, матрицы или разметки.

Gold не передаётся анализирующему агенту во время рабочего запуска и не должен
использоваться как подсказка с конкретными номерами пунктов.

### 9.2. Основные метрики

- **Soft mapping accuracy**: mapping считается успешным, если множество
  предсказанных `matrix_ids` пересекается с проверенным пулом кандидатов для
  того же пункта договора.
- **Status accuracy**: доля всех операционных пунктов договора, для которых
  предсказан правильный статус.
- **Status accuracy on soft-mapped items**: точность статуса только среди
  пунктов, где найден допустимый mapping-кандидат. Метрика отделяет ошибку
  классификации от ошибки поиска аналога.
- **Deviation precision / recall**: точность и полнота класса `deviation`.
- **Extra precision / recall**: точность и полнота класса
  `extra_in_contract`.
- **Missing precision / recall**: точность и полнота класса
  `missing_in_contract` по ID строк матрицы.

Evaluator также рассчитывает TP, FP, FN и технически сохраняет F1, однако для
диагностики проекта основными являются отдельные precision и recall: они
показывают, создаёт ли skill лишние риски или пропускает размеченные юристами
расхождения.

Время полного запуска и длительность отдельных model/tool вызовов являются
обязательными эксплуатационными метриками. Рост точности не должен достигаться
за счёт неограниченных повторных проверок без подтверждаемой прибавки качества.

## 10. Как улучшаются метрики

Качество улучшается преимущественно через изменение domain skill, а не через
добавление детерминированной юридической логики в Python-код.

### 10.1. Принцип разделения инструкций

- `prompts/orchestrator-system.md` определяет роль, границы работы, доступ к
  skill, файловую дисциплину и требования к сохранению результата.
- `prompts/contract-review-user.md` формулирует конкретную задачу, пути
  входов/выхода и проверяемые критерии завершения, но не юридическую методику.
- `skills/contract-matrix-review/SKILL.md` задаёт назначение, источники,
  нормативную иерархию и единицы анализа.
- `references/business-deviation-policy.md` является единственным подробным
  источником метода сопоставления и правил статусов.
- `references/business-casebook.md` содержит исчерпывающую типологию целевых
  бизнес-дельт и по одному независимому примеру на класс.
- `references/output-schema.md` определяет только формат результата и его
  инварианты.

Одно правило не должно независимо пересказываться в нескольких слоях. При
расхождении example и policy приоритет имеет policy. Повторы, отрицательные
инструкции о действиях, которые агент и так не собирался выполнять, и
двойственные quality checks увеличивают контекст и время рассуждения без
гарантированной прибавки качества.

### 10.2. Цикл калибровки

1. Зафиксировать версию договора, матрицы, skill и полный `result.json`.
2. Посчитать метрики на verified gold и получить конкретные mapping/status FP
   и FN.
3. Для каждой ошибки определить её источник:
   - реальная ошибка поиска аналога;
   - ошибка границы `aligned` / `deviation` / `extra_in_contract`;
   - ложный или пропущенный `missing_in_contract`;
   - неверно определённая применимость selector;
   - неоперационный пункт, ошибочно попавший в оценку;
   - дефект или устаревшая версия gold;
   - инфраструктурная ошибка пути, публикации или неполного артефакта.
4. Если ошибка относится к юридическому решению агента, сформулировать
   минимальное обобщаемое правило и внести его в один подходящий файл skill.
5. Добавить или изменить casebook-пример только тогда, когда без примера
   граница правила остаётся неоднозначной. Пример не должен содержать уникальные
   номера или текст тестового договора, позволяющие запомнить gold.
6. Провести аудит skill на противоречия, повторы, не относящиеся к сценарию
   запреты и конфликтующие примеры.
7. Повторно запустить не только документ, на котором найдена ошибка, но и весь
   доступный регрессионный набор: Kaluga, Kuzbas, Irkutsk и остальные
   проверенные договоры.
8. Сравнить mapping, status, per-class precision/recall и runtime с предыдущей
   версией. Изменение принимается только при воспроизводимом улучшении целевой
   ошибки без необъяснимой регрессии на других документах.
9. Зафиксировать причины ошибок и решение в `errors.md`, а версию skill и
   результаты запуска — в истории Git и артефактах оценки.

### 10.3. Приоритеты улучшения

Так как soft mapping исторически работает лучше классификации, основной фокус
калибровки — точная граница статусов:

- `deviation` против редакционного различия, допустимой конкретизации или
  неактивного варианта;
- `deviation` против `extra_in_contract` в смешанном пункте;
- `extra_in_contract` против неоперационного текста;
- частичное покрытие как `deviation`, а не `missing_in_contract`;
- настоящий missing против optional- или неподтверждённо применимой строки;
- существенный placeholder против пассивного реквизита;
- прямая несовместимость против простого отсутствия повторения детали.

Текущий casebook является исчерпывающим перечнем C01–C21 именно для границы
`deviation` / `aligned`, но не списком разрешённых mappings или конкретных
номеров gold. Он обобщается по правоотношению, изменённому элементу и типу
изменения. Расширение перечня — отдельное бизнес-решение после разбора ошибки,
а не автоматический перенос любой новой текстовой дельты в deviation.

### 10.4. Что нельзя использовать для искусственного роста метрик

- подстановку конкретных gold-номеров или ответов в prompt/skill;
- использование нумерации как сигнала matching;
- изменение gold только для согласования с очередным ответом агента;
- скрытый классификатор статусов в quality gate;
- заранее встроенные embeddings, векторный поиск, retrieval/reranking,
  доменный shortlist-tool или классификатор;
- исключение сложных операционных пунктов из оцениваемой выборки;
- повторные модельные проходы без измеримого эффекта;
- оптимизацию только одного договора без регрессии на остальных.

## 11. Нефункциональные требования

- Полный договор, относящиеся приложения и вся матрица должны быть рассмотрены
  до завершения анализа.
- Исходники доступны агенту только для чтения; итоговый файл пишется в
  `outputs` рабочего пространства.
- Все текстовые и JSON-файлы обрабатываются в UTF-8.
- Результат должен быть воспроизводимо читаемым программой и соответствовать
  `contract-matrix-map.v6`.
- Комментарий должен называть конкретное основание статуса, а не общую оценку.
- Harness не ограничивает способ исследования документов и использование
  стандартных инструментов агента.
- Ошибка или невалидный результат не должны уничтожать диагностический
  workspace.
- Audit trace не содержит полный договор, prompts или payload инструментов;
  содержательный console log допускается только в защищённой среде.
- Любое изменение skill должно сопровождаться тестом согласованности
  инструкций и регрессионным измерением качества и времени.

## 12. Тестирование и критерии приёмки

### 12.1. Автоматические тесты harness

Тесты должны подтверждать:

- корректное монтирование единственного domain skill и входных файлов;
- валидацию расширений и путей;
- отсутствие дублирования юридических правил в prompts;
- целостность структуры skill и обязательных references;
- нормализацию виртуальных путей на Windows и защиту от записи в `C:\outputs`;
- точность механического quality gate;
- сохранение thread ID при model retry и полную замену thread/session при
  неоднозначном execute;
- публикацию result/trace/manifest с manifest последним;
- полный контракт AEF backend, path traversal, защищённые корни, UTF-8,
  literal grep/glob, heartbeat, TTL, retry/restart и отсутствие секретов в
  логах;
- очистку успешного workspace и сохранение failed workspace;
- корректную конфигурацию модели, лимитов и таймаутов.

Дополнительно проверяются env/CLI precedence, запуск без аргументов, сохранение
UTF-8 в консоли, переключение full/compact, маскирование секретов, отсутствие
содержательных данных в trace, реальный GigaChat adapter с mock HTTP и цикл
model → инструмент/general-purpose → model. Тесты на подставных ответах
проверяют интеграционный контракт, не интеллект или качество `glm-5.2`.

Команда локальной проверки: `python -m pytest -q`.
Последняя подтверждённая проверка: **125 passed, 2 skipped**.
Оба skip — opt-in live WorkStation тесты. Реальные вызовы корпоративных
сервисов на устройстве разработки не выполнялись по ограничению доступа.

На корпоративной машине, отдельно от обычных тестов:

```powershell
$env:RUN_AEF_LIVE_TESTS = "1"
python -m pytest -q tests/test_aef_live.py
```

Для дополнительного heartbeat-теста дольше 15 минут установить также
`RUN_AEF_LONG_LIVE_TESTS=1`. Тесты создают реальные сессии, загружают тестовые
данные и выполняют команды; включать их осознанно. После smoke нужен полный
canary одного документа и затем нескольких повторов каждого verified-gold
документа. Измерить качество и runtime заново: старые DeepSeek-метрики не
являются доказательством качества нового GigaChat/GLM-профиля.

### 12.2. Критерии приёмки изменения skill

Изменение считается готовым, если:

1. все автоматические тесты проходят;
2. skill, policy, schema и examples не противоречат друг другу;
3. целевая ошибка подтверждённо устранена на документе, где она была найдена;
4. на остальных verified gold-наборах нет необъяснимой регрессии mapping,
   status и per-class precision/recall;
5. рост runtime объясним и соразмерен измеренному улучшению;
6. итоговый `result.json` проходит механический gate без ручного исправления;
7. изменения и результаты зафиксированы так, чтобы прогон можно было
   воспроизвести по тем же версиям входов и skill.

Числовой порог релиза в репозитории пока не закреплён. До его утверждения
решение принимается сравнением с последним зафиксированным baseline по всему
регрессионному набору, а не по одному успешному запуску.

## 13. Ограничения и известные риски

- Юридические XLSX могут содержать пропуски, устаревшие matrix ID и
  неоперационные строки; поэтому raw gold нельзя считать автоматически
  корректным.
- Генеративный агент может давать разные результаты на повторных запусках даже
  при `temperature=0`, особенно при больших контекстах и длинных цепочках
  инструментов.
- Противоречивые, повторяющиеся или чрезмерно частные инструкции ухудшают
  статусную калибровку и увеличивают runtime.
- Слишком узкий список примеров приводит к переобучению на известных
  договорах; слишком широкий список размывает границы классов.
- Quality gate гарантирует форму артефакта, но не юридическую корректность.
- Текущий проект является CLI/harness и не содержит отдельного интерфейса для
  юриста, системы согласования заключения или хранилища результатов.
- Минимальная поддерживаемая версия Python и формальные целевые SLA по времени
  и метрикам пока не определены.
- Live WorkStation/GigaChat совместимость, квоты контекстного окна и качество
  `glm-5.2` ещё не подтверждены canary-прогонами в корпоративной сети.
- HTTP 504 execute в текущем коде трактуется как завершённый timeout. Нужно
  подтвердить этот контракт на стенде: gateway 504 сам по себе не всегда
  доказывает остановку серверной команды. Это известное интеграционное допущение.
- Проверка SHA после execute обнаруживает изменение исходников, но не
  предотвращает произвольные внешние эффекты агентского кода.
- Результат, trace и manifest не являются одной файловой транзакцией.
  При аварийной публикации требуется сверка manifest/SHA; два одновременных
  процесса не должны публиковать по одному пути.
- Полный console log может быть очень большим: каждый модельный вход включает
  доступный на этом шаге контекст. Маскирование секретов не заменяет контроль
  доступа и политику хранения логов.

## 15. Диагностика и эксплуатация

| Симптом | Проверка / действие |
|---|---|
| `Provide --contract or set AGENT_CONTRACT_PATH` | Заполнить `.env` рядом с main.py либо передать CLI-пути |
| Не найден входной файл | Для env-пути проверить корень проекта; для CLI — cwd; не подставлять виртуальный `/inputs/...` вместо локального файла |
| TXT/JSON validation error | Исправить кодировку/контейнер входов; gate не делает OCR и не восстанавливает нумерацию |
| Ошибка `GIGACHAT_HOST`/`PORT` | Проверить hostname без схемы, порт и endpoint; `DEEPSEEK_*` больше не используются |
| TLS verification failed | Проверить CA нужного сервиса, цепочку доверия, cert/key и `LOCAL=true`; не делать HTTP fallback |
| WorkStation preflight/DNS timeout | Запустить в корпоративной сети с DNS/VPN/ИФТ; локального fallback нет |
| GigaChat 401/403/404 | Проверить разрешения gateway, mTLS и имя модели `glm-5.2`; повторы не исправляют конфигурацию |
| Долго нет текста модели | При streaming=false ответ появляется в конце вызова; смотреть model_start и timeout 300 секунд |
| Read/transport error модели | Смотреть retry-события и здоровье WorkStation; не смешивать с execute timeout |
| `AefAttemptLost` | Смотреть причину restart; следующая разрешённая попытка начнёт анализ заново |
| TTL/quota incompatibility | Сверить полученные expiresAt и квоты; heartbeat не продлевает absolute TTL |
| Source SHA mismatch | Исходники изменились; не публиковать результат этой попытки |
| Structural gate failed | Использовать сохранённый staging и failed trace/manifest; исправление юридических правил — отдельная задача |
| Старый JSON сохранился после ошибки | Проверить свежий manifest/status/SHA; это не результат нового неудачного запуска |

Переход на production WorkStation — явная настройка нового HTTPS origin и CA,
не переписывание backend и не автоматический fallback. Доступность API и
канареечные прогоны должны быть проверены до смены рабочего профиля.

## 16. Воспроизводимая оценка качества

Пример отдельной оценки уже завершённого результата:

```powershell
python benchmarks/evaluate_verified_gold.py `
  --gold benchmarks/kaluga_adjudicated_gold.v1.json `
  --prediction outputs/kaluga.json `
  --output outputs/kaluga.metrics.json
```

Версия gold выбирается по проверенному документу и истории исправлений, не
просто по наибольшему номеру файла. Команда не запускает агента и не меняет
его итоговый JSON. Для soft mapping знаменатель — gold-вхождения с непустым
mapping; для status accuracy — операционные gold-вхождения. Missing считается
по ID матрицы отдельно. `precision=TP/(TP+FP)`, `recall=TP/(TP+FN)`;
при нулевом знаменателе evaluator возвращает `null`, а не вымышленные 100%.

Evaluator имеет техническую нормализацию ID и эвристическое сопоставление
повторных вхождений по locator. Это только offline измерение, не инструменты
аналитического агента. Спорные совпадения и ошибки нумерации требуют ручной
сверки с TXT/матрицей/gold до вывода о качестве. Доказательство улучшения —
артефакты повторных запусков, версии источников/skill, TP/FP/FN и runtime,
а не успешное прохождение pytest или вручную повышенная таблица метрик.

## 17. Граница текущей поставки

Реализованы CLI/harness, корпоративный model adapter, AEF backend/lifecycle,
публикация артефактов, подробная консоль, доменный skill и offline evaluator.
Не реализованы отдельный web/API-сервис для юриста, UI, очередь заданий,
постоянная база запусков, S3 persistence, автоматический production rollout,
OCR, redline и экспорт XLSX из основного рабочего CLI. Данные XLSX используются
для gold-аудита. Подключение WorkStation не переносит orchestration/model API
в сам сервис и не требует изменения его серверной реализации.
